04共用契约与兼容策略

主题九次交付共同遵守的决定
身份AppId 是安装身份；InstanceKey=(boot_nonce, slot, epoch) 是运行身份；ComponentKey 增加组件种类、ID 和组件 epoch。owner 从 Host 调用上下文取得，不信任 Guest 自报 AppId。
状态机Guest：STOPPED / STARTING / RUNNING / SUSPENDED / STOPPING。Activity：NONE / CREATED / RESUMED / STOPPED。Service：STOPPED / STARTING / RUNNING / STOPPING。失败作为退出原因，不另建 CRASHED 状态。
单写入者AppManager 控制循环独占状态迁移；慢加载、执行、I/O 和回收在有界执行器运行。Accepted 只表示入队，READY、首帧提交和 EXITED 分别确认。
显示与输入一个活动 DisplayLease、一个受预算的 staging；前台交接以有效组件首帧为条件。旧实例 / 旧组件帧和输入不能提交。Home / 系统提醒优先。
组件资源Activity 资源域拥有 UI / 输入；Service 资源域拥有媒体 / 后台请求；App 资源域拥有共享账号和配置。ComponentContext 显式绑定资源域，异步完成保留原 ComponentKey，不依赖可变的“当前组件”。
组件 token 的边界它用于生命周期与路由；同 Guest 共享内存，不构成恶意 Activity 与 Service 之间的安全边界。Host 必须校验 token 属于当前 Guest 及有效组件代次。
兼容保留 Bundle v1 外壳，扩展版本化 requirements。新 Host 将旧 v1 App 作为 LegacyActivity，在多应用 profile 下不授予后台 Service / Widget 权限；旧 Host 对新必需版本明确拒绝。
ABI新增服务 / 方法 / 事件分配新 ID；不复用旧 ID，不暴露 STL / C++ 布局 / Host 指针。端点继续放在现有 ABI 文件边界内，业务实现委托给 Runtime / Host 模块。
WAMR / AOT不升级或修改 WAMR / wamrc，不改 AOT 格式；每 Guest 独立 module instance、exec_env、可变内存和执行任务，全局 runtime 初始化一次。保留内存 / 栈检查，拒绝 unchecked-memory。
消息Host 中转、复制小载荷、有界邮箱、Read / Ack 票据。入队、接收、业务完成分开；默认易失，不承诺跨崩溃重放。payload 不塞入固定 Event 结构。
后台资格MEDIA、JOB、WIDGET_ACTION 都是有 owner 的执行资格。Service 的 RUNNING 不等于一直占 CPU，也不自动赋予永久常驻权。Host 闹钟不依赖 Guest 存活。

PC 与 RTOS 共用状态模型和中立的 Runtime 控制接口。拟新增 runtime/app_control.hpp / session_runner.hpp 提供请求和通知契约，由组合根注入 Host 实现；Runtime 不反向包含 Host controller。Guest SDK 继续不依赖 LVGL、SDL、FreeRTOS 或 POSIX。

迁移使用同一代码的并发容量 / 能力 profile，不维护两套 Home 或音乐页面。D1 保持现有单会话行为；D2–D3 在显式开发 profile 中启用并发；D4 验收迁移后的音乐；D7 功能闭环后再切换 PC 默认配置。新的后台资格只来自受 Host 核验的组件声明。

05D1：建立实例资源归属

前置：当前单 Guest 基线可运行结果：仍为单 Guest，资源清理已局部化粗估：3–5 人日

实施任务

  1. 新增中立 InstanceKey、OwnerScope、资源计数与代次校验；记录物理设备、App 资源和实例资源的归属。
  2. 为 Graphics / Input / Audio / HTTP / URL media 建立每实例服务视图。图形包括 Scene、纹理、字体、Direct Surface 和异步解码，不只是给 StopAll 换名字。
  3. 移除 Guest 初始化 / 挂起 / 析构对其他 owner 的全局 ResumeAll / SuspendAll / StopAll / ReleaseGuestResources 副作用。系统整体关机仍可使用全局设备操作。
  4. 为输入接收者、PCM 完成通知和媒体句柄建立 owner 路由；异步回调持有安全租约，确认关闭后排空。
  5. 把 PC 全局 JoinTasks 的会话用途改为 TaskGroup / owner 回收。共享网络执行器和任务池有固定容量，Guest 停止不能等待或结束其他实例的任务。
  6. 在统一 Host 测试 wrapper 中增加便携应用框架测试分组；仅该分组可独立于 esp-http3 运行，保留原固件全量测试的依赖检查。直接调用编译器不作为测试入口。

代码位置：GuestContext、DeviceServices、设备契约、Runtime 图形 / 音频 / 资源服务、PC 任务兼容层、PC remote / audio；拟新增 Runtime owner 与 scoped-services 类型。

建议提交边界

D1.1：owner 类型、固定容量与测试夹具；D1.2：作用域服务及局部清理；D1.3：任务 / 回调排空和现有单 Guest 回归。生产配置本阶段仍保持一个 Guest。

验收与交付证据

  • 两个 Host 测试上下文分别创建资源，关闭 A 后 B 的音频、纹理、请求与输入绑定不受影响；这是 owner 测试，不假装已实现多 Guest。
  • 旧 owner / 旧 generation 的回调被丢弃；A 的资源计数归零，B 的有效资源计数保持。
  • 现有单 Guest 的 Home 后台播放、市场、音乐、登录、图形与 Direct Surface 回归通过。
  • 交付资源归属清单、释放顺序、自动化测试、构建结果及一份按 owner 的资源快照。

回退边界：保持单槽 profile；若作用域语义未通过，不启用 D2 并发。回退以整个未完成提交组为单位，不用恢复全局清理来掩盖局部错误。

06D2：AppManager 与原生多实例

前置：D1 全部 owner 验证通过结果：两个测试 Guest 共存与切换粗估：4–6 人日

实施任务

  1. 新增无 LVGL 依赖的 AppManager、固定 AppRecord / InstanceSlot、命令队列、关键通知邮箱和 ManagerSnapshot；先以单槽替换 PC main 的管理策略。
  2. 建立 SessionRunner 的 BeginStart / RequestSuspend / RequestResume / RequestStop 和完成通知。不能在 UI 控制循环调用会阻塞的 Stop / join。
  3. 实现 Guest 五状态与 seq / epoch 验证；挂起在 event_wait 安全点确认，恢复先开控制门，再投递普通事件；停止仍等待退出和排空。
  4. 以两个小 Guest 验证并发，每实例一个受控 Host 执行任务；WAMR 全局只初始化一次。PC 快速解释器加载会改写输入模块，因此每次加载保留独立可写字节副本。
  5. 实现唯一 DisplayLease、InputRouter 与一个 staging；新前台首帧未准备好时保留旧前台。Home 可取消待提交切换，连续请求以最新用户意图为准。
  6. 加入 PackageRevision 租约：升级 / 卸载仅协调目标 App，等其退出和映射释放后替换；其他 Guest 继续。槽满明确拒绝，不自动回收。

代码位置：PC main、Session、PC 渲染 / 输入与 Home；拟新增 host/controller/app_manager.*、状态模型和 Runtime runner 契约，并加入 PC CMake。MCU 原 AppRuntime 此时仍保持单会话 profile。

建议提交边界

D2.1：纯状态机与单槽接入；D2.2：两个测试 Guest 的实例集合 / 路由；D2.3：准备后交接、异步停止和包租约。后台测试资格由可信测试组合根配置，不开放 Guest 自行声明任意后台权限的入口。

验收与交付证据

  • 两个 Guest 的心跳同时递增；切换 A/B、返回 Home、停止 A 后，B 继续且 InstanceKey 不变。
  • 只有当前前台收到触摸、按键与文本；切换取消原拖动，旧文本不会进入新页面，后台帧不能覆盖前台或 Home。
  • 连续激活 A→B→A、加载时返回 Home、启动失败、满槽和队列满，均保留合法的显示目标及预算。
  • 开始停止后 UI 控制循环仍能响应；迟到 READY / QUIESCED / EXITED 不复活旧实例；100 次正常启动 / 停止后资源回到稳定基线。
  • 交付状态迁移测试、并发 Guest 夹具、管理快照，以及双 Guest 运行 / 切换 / 退出的日志和截图。

回退边界：同一 AppManager 使用单槽配置继续运行既有功能；并发 profile 在验收前不成为默认。此阶段不把未迁移的音乐 App 当正式后台 Service 验收。

07D3：Activity / Service SDK 与兼容声明

前置：D2 多实例管理稳定结果：组件生命周期可由 Host 协调粗估：4–6 人日

实施任务

  1. 新增 Guest 组件注册、Activity / Service 基类或等效 typed 接口和 ComponentContext；继续复用一个 Application 事件循环，生命周期与业务事件串行分发。
  2. 实现 Activity 创建、首帧就绪、恢复、隐藏和销毁；实现 Service 启动、就绪、停止与工作完成。回调 ACK 不等于整个 App 已退出。
  3. 为 UI / 输入、Service 媒体 / 请求和 AppModel 建立明确资源子域。回调绑定原组件代次，销毁 Activity 不关闭 Service 资源。
  4. 通过 Service ABI 传递版本化生命周期及组件 token，不新增 Core import。固定 Event 仅携带控制字段 / 票据，不包含任意长载荷。
  5. 同步工具、Host 和 Guest 的 requirements 新版本：组件声明、后台能力、所需服务版本和 Widget 预留声明；旧 v1 App 映射为 LegacyActivity。
  6. 一次盘点后续 Lifecycle / Message / Widget / Job / Alarm 服务 ID 与容量。按需固定扩大 ServiceRegistry（初始建议 24），登记内存成本；尚未实现的能力不在描述符中虚报支持。

代码位置：SDK Application、Guest Runtime、ABI、现有 service_endpoints / registry、打包工具、CLI、requirements reader；拟新增组件分发器与 conformance Guest。Host ActivityController / ServiceController 为 AppManager 内的控制块，不各自开管理线程。

建议提交边界

D3.1：ABI / requirements 契约与兼容 fixture；D3.2：SDK 分发和 Host 控制；D3.3：组件资源域及 conformance。每个公开版本变更同步示例和文档，不在计划阶段提前占用最终数值 ID。

验收与交付证据

  • 测试 App 销毁 Activity 后 Service 心跳继续；重建 Activity 产生新组件 epoch，Guest main 只运行一次。
  • 停止 Service 不销毁仍在前台的 Activity；旧组件 HTTP / UI 回调不进入新组件。
  • 旧 v1 包可在新 Host 启动；多应用 profile 下无后台权限；不支持新必需版本的 Host 明确拒绝。
  • 对畸形大小、无效组件、跨实例 token、重复迁移和超容量请求有确定结果；Guest SDK 不引入 OS / LVGL 依赖。
  • 交付 SDK 最小组件示例、协议表、manifest 示例、新旧 requirements fixture 与兼容测试。

回退边界：阶段能力在 Host profile 中关闭，新包保留明确版本要求；不把新 requirements 当 v1 结构解释，也不为兼容复用旧事件 ID。

08D4：网易云音乐迁移为 Activity＋PlaybackService

前置：D3 组件 SDK 与资源子域结果：正式音乐后台播放与其他 Guest 共存粗估：3–5 人日

实施任务

  1. 拆分 AppModel、MusicActivity 与 PlaybackService。账号 / Cookie 和共享配置属于 AppModel；Scene、列表滚动和页面临时请求属于 Activity；队列、媒体句柄、自动下一首和曲目解析属于 Service。
  2. 区分页面读取、账号登录和播放关键请求。HTTP 改为每实例至少两个有界请求名额，给 PlaybackService 预留一个；物理执行器也需要并行通道，不能只增加句柄却继续单线程阻塞处理长轮询。
  3. 实现有效媒体租约：可播放的加载 / 播放工作获得资格，用户暂停进入宽限；返回 Home 或进入其他 App 不撤销媒体资格。后台 Activity 停止动画与帧提交。
  4. 销毁 / 重建 MusicActivity 时从 AppModel 和媒体状态重建页面；不重登账号、不重建播放队列、不重复启动 Guest。
  5. 保持现有微信官网授权、每日推荐去重、触底加载、红星收藏和独立播放队列行为；升级 App requirements 和组件声明。
  6. 退出账号、切换账号或会话失效时，同步撤销 Service 中的私有请求、队列和个人快照；Activity 重建不能恢复另一个账号的内存状态。
  7. Service 不依赖 Activity 对象指针。D5 之前 Home 暂用受控管理快照显示运行 App，跨界面媒体卡片待统一 Widget 协议接入。

代码位置：音乐入口、客户端、界面、账号 / 登录模块、app.json、Guest Network / Audio facade、Host 网络池与媒体资源路由。保留一个新的正式页面实现，不维护旧 UI 分支。

建议提交边界

D4.1：AppModel / Activity / Service 拆分与单 App 回归；D4.2：HTTP 并发与媒体资格；D4.3：音乐＋前台测试 Guest 的集成。生产账号扫码仅用于必要的手动联调，自动回归全部使用合成音频和本地接口 fixture。

验收与交付证据

  • 音乐后台连续完成至少两首测试歌曲并自动下一首，前台测试 App 可正常交互。
  • 销毁并重建 MusicActivity 后仍是同一 Guest / Service，昵称、账号身份、队列及当前播放位置保留。
  • 一个请求模拟 35 秒登录长轮询时，Service 的下一首解析可独立完成；关闭 Activity 请求不取消播放请求。
  • 停止整个音乐 App 后仅清理音乐 owner；其他 App 的网络、计时和显示继续。
  • 交付新的音乐 Bundle、组件职责说明、并发请求测试、PCM 证据和后台运行日志；不记录真实凭证。

回退边界：默认 profile 仍可限制单槽，组件实现保持一致。若新旧应用包的 requirements 不兼容，应回到匹配 Host / Guest 的已验证组合，不通过忽略版本检查强行运行。

09D5：Home Widget、操作与实例消息

前置：D4 音乐业务独立于页面结果：Home 展示并控制多个 App粗估：3–5 人日

实施任务

  1. 新增 WidgetStore：AppId 所有权、模板、版本、更新时间、过期 / 离线标记和有界状态快照；Home 仅渲染允许字段，不读 Guest 对象或 Cookie。

  3. 新增 MessageBroker、票据 Read / Ack 和 Result；Host 注入发送者，校验目标实例 / 组件代次、导出权限、载荷及期限。同 Guest 组件消息与跨 Guest 消息统一经过 Broker，不直接跨调 Guest 函数。

  5. 实现活跃实例内的序列水位和有界结果缓存；旧序列落在缓存外时拒绝，不重新执行“下一首”。普通消息不持久化、不自动跨实例重放。
  6. 增加实例地址与逻辑 App / Service 地址的区分。D5 先向存活接收端路由；自动冷启动入口在 D6 结合任务资格开放。默认私有，导出服务必须声明调用者 / 消息类型 allowlist。

代码位置：Home、Host WidgetStore / MessageBroker（拟新增）、AppManager 操作入口、Runtime 消息邮箱、Guest Widget / Message SDK、音乐 Service 快照发布。Runtime 通过注入的中立接口请求 Host 操作。

建议提交边界

D5.1：快照协议与模板渲染；D5.2：Broker / Ack / 权限 / 去重；D5.3：音乐卡片与多应用 Home 接入。卡片模板不嵌入另一 Guest 的 Scene 或 LVGL 树。

验收与交付证据

  • Home 同时显示三个来源的卡片；音乐进度可由 Host 时间推算，常规发布不超过设定频率。
  • Home 暂停 / 恢复 / 下一首后，音乐页面显示同一业务结果；进入页面不丢队列。
  • 超大快照、邮箱满、未授权发送者、旧 Widget revision 和旧 ComponentKey 都被明确拒绝。
  • 重复 NextTrack 只执行一次；重启后的新实例不接收旧实例回复；没有普通消息“恰好一次”假承诺。
  • 交付 Widget / Message 线协议、权限 fixture、Host 模板截图和按请求关联的路由日志。

回退边界：Home 可退回仅显示 App 列表和管理快照；组件继续使用同一生命周期。关闭 Widget 能力时通过协商明确告知 Guest，不保留会被错误投递的旧按钮。

10D6：天气应用与 Host JobScheduler

前置：D5 Widget / Broker；真实数据源在接入前确定结果：按时间 / 消息执行后台工作并休眠粗估：3–5 人日

实施任务

  1. 新增 Host JobScheduler：按 AppId 持久登记周期 / 单次任务；运行时创建有限 work ticket，使用单调时钟限制执行 deadline。周期刷新不是精确闹钟。
  2. 闭合 EnsureWork：RUNNING 复用、SUSPENDED 安全恢复、STOPPED 受控冷启动。Guest / Service Ready 后才投递工作；一个旧 work 完成不能停止仍有其他工作的 Service。
  3. 实现有限消息唤醒：逻辑端点必须显式允许、来源合法、具有预算，且不是用户停止状态。实例端点的迟到消息永不改投到新实例。
  4. 新增 guest/apps/weather/（拟新增）：WeatherActivity 展示详情，WeatherService 发请求、更新缓存和 Widget，然后完成工作。默认刷新周期可取 15 分钟，测试使用虚拟时间。
  5. 加入后台资格与空闲策略：有 MEDIA / JOB / WIDGET_ACTION 时不挂起；无资格且无前台 / 待投递操作时经安全点挂起。本轮不做内存压力自动回收。
  6. 持久保存城市、任务计划和最后成功天气；失败保留旧值并标记时间。用户 StopApp 设置 user_stopped，阻止自动 Job / 消息拉起；显式打开或用户 Widget 操作可清除标记。

代码位置：Host JobScheduler / 任务登记存储（拟新增）、AppManager 后台资格和工作租约、Runtime Job SDK、天气 Guest；复用既有 HTTP，不在天气中引入 socket 或平台头文件。

数据源与提交边界

WeatherClient 隔离城市标识、认证和响应解析。先用 localhost fixture 覆盖成功 / 失败 / 慢响应；真实数据源、城市配置和授权条件在 D6 接入前确定，密钥不写仓库。D6.1：Scheduler / work ticket；D6.2：天气组件 / Widget；D6.3：真实来源适配及冷 / 热唤醒验证。

验收与交付证据

  • 虚拟时间触发任务，覆盖 RUNNING、SUSPENDED、STOPPED 三条路径；刷新后卡片更新，Service 无工作时结束 / 挂起。
  • 刷新期间音乐不断；Guest Timer 在挂起时冻结，而 Host 时钟、Job 时限与未来登记不冻结。
  • 慢请求超过工作总 deadline 后取消 I/O，释放对应租约；已有天气成功值保留。
  • user_stopped 阻止自动拉起；显式 Widget 刷新可启动目标 App，且不抢当前 Activity 前台。
  • 正常重启可恢复配置和未来计划；卸载删除相关 Job。交付天气 Guest、数据源说明、虚拟时钟测试和一次真实刷新结果。

回退边界：关闭自动调度后保留手动打开 / 刷新；任务登记采用版本化记录，不因临时关闭功能而损坏旧配置。真实源未确定时，D6 可进入 fixture 联调，但不能标记真实天气验收完成。

11D7：时钟闹钟、Host AlarmScheduler 与音频焦点

前置：D6 调度与持久登记；D4 媒体 Service结果：PC 三应用功能闭环粗估：4–6 人日

实施任务

  1. 新增 guest/apps/clock-alarm/（拟新增）。ClockActivity 负责设置、启用 / 停用闹钟，配置提交给 Host；ClockService 可按需接收通知，不在响铃关键路径上。
  2. Host Time / Clock Widget 独立刷新；单调时钟用于 deadline，UTC 与固定时区偏移用于闹钟。首版不引入完整 IANA 时区 / 夏令时数据库。
  3. 实现 AlarmScheduler 与版本化持久记录：一次性与按星期重复、停止响铃、未来计划恢复；闹钟登记的确认必须在持久提交成功之后返回。
  4. 时间未同步时标记不可用，不按错误 UTC 响铃。显式校时 / 改时区后重算未来 occurrence；首版不补响关机或时间跳变期间错过的提醒。同一 occurrence 去重，多条同时到期合并为一个 Host 响铃界面。
  5. 实现 AudioFocus：Host 闹钟取得优先级，暂停或 duck 音乐，记录媒体 owner、句柄代次和 intent_version。用户暂停、停止或切歌后，不得用旧快照恢复错误媒体。
  6. 区分用户暂停与 focus 中断；后者不能误触发音乐的用户暂停回收计时。系统主音量继续由 Host 管理。
  7. 用户“关闭 App”保留已确认的 Host 闹钟，且不拉起被停止的 Guest；停用禁用闹钟，卸载 / 清除数据删除闹钟。界面明确表达此产品规则。

代码位置：Host Time / AlarmScheduler / AudioFocus / 闹钟系统 UI（拟新增）、Host 持久配置、AppManager 停用 / 卸载协调、Audio 服务、Clock Guest、音乐 Service 的 focus 事件。

建议提交边界

D7.1：时间模型、虚拟时钟与持久闹钟；D7.2：ClockActivity、Host 卡片与响铃；D7.3：音频焦点和三应用联调。贪睡、多级提醒、自定义网络铃声后置，使用一条有界 Host 铃声路径完成首版。

验收与交付证据

  • Clock Guest 正常停止 / 回收后，Home 时间仍更新；已确认闹钟仍按计划响铃，Guest 通知失败不影响铃声。
  • 覆盖一次性、每周重复、关闭 / 停用 / 卸载、正常重启、UTC 前后跳变、时区调整与多个同时到期；同一 occurrence 不重复响铃。
  • 响铃结束恢复仍有效的播放意图；用户在响铃期间暂停或停止音乐，则不恢复；旧媒体 owner / generation 不被误用。
  • 天气刷新、音乐后台、ClockActivity / Home 切换同时有效；操作不阻塞 LVGL，系统弹窗拥有输入优先级。
  • 交付时钟 Guest、登记格式、音频焦点状态表、时间推进测试、PCM 和三应用演示。

回退边界：有未处理闹钟时不通过关闭能力静默丢弃登记；保留读取 / 禁用 / 删除配置的路径。默认多应用 profile 仅在本阶段功能闭环通过后启用；必要时回到单槽配置和匹配的应用版本。

12D8：把 RV32 AOT 接入同一框架

前置：D7 原生 PC 功能闭环结果：原生 Wasm / RV32 共用管理与业务契约粗估：3–5 人日

实施任务

  1. 将 RV32 Session 适配为相同 SessionRunner，启动、前台、挂起、工作资格和退出只由 AppManager 决定，不在后端复制另一套策略。
  2. 每实例独立 QEMU 进程、socket、共享 RAM、桥接状态、包映射与日志 owner；包租约和内存 / 子进程预算都纳入准入。
  3. 使用原七个 Core imports 透传新 Service；核对消息票据、生命周期、Widget、Job / Alarm 的请求大小、分块和指针范围。仅在 framing 确有变化时显式协商协议版本。
  4. 构建支持新 SDK 的音乐、天气、时钟 RV32 Bundle，保持 WAMR / wamrc 固定版本和 AOT v6，不要求改写旧机器码。
  5. 官方旧 Bundle 保留 LegacyActivity 前台兼容；不能因 Host 升级就虚构 Service 或 Widget。打开系统页面时按其能力执行挂起策略，返回复用原实例。
  6. 为原生 / RV32 测试分别设置启动时限；优先等待明确就绪条件。模拟器更慢不作为业务断言失败的依据，也不把放宽时限当性能达标证据。

代码位置：RV32 Host 桥、runner、framing、SessionRunner、构建工具和原生 / RV32 共用的测试场景。若桥已能透传新服务，保持协议和 runner 改动最小。

建议提交边界

D8.1：runner 接口与多桥归属；D8.2：新 Guest Bundle / 服务透传；D8.3：混合后端与官方旧包回归。QEMU 进程终止是 PC 提供的能力，不用它推导 MCU 任意故障可恢复。

验收与交付证据

  • 至少两个 RV32 Guest 共存，停止一个不会结束另一个进程、流或 socket；旧桥回调不能落到新槽。
  • 原生音乐＋RV32 测试 App，以及 RV32 音乐＋原生测试 App 均可前后台切换；有效资源归属相同。
  • 新音乐 RV32 Bundle 通过登录 fixture、列表、收藏、每日推荐、播放与后台自动下一首；天气、闹钟通过同一虚拟时间测试集。
  • 官方固定旧包可浏览、安装、校验、运行、返回 Home 和再次进入；畸形 IPC、越界范围和错误版本仍拒绝。
  • 交付各 Guest release Bundle、后端一致性结果与能力矩阵，不提交生成的二进制或测试报告到源码树。

回退边界：关闭 RV32 多实例能力时原生路径仍可使用；旧包安装与数据不删除。任何桥版本变化必须明确拒绝不兼容对端，不能尝试按旧结构继续解析。

13D9：一块 RTOS / no-MMU 目标板适配

前置：D8；明确板卡、屏幕、RAM / PSRAM、音频与网络能力结果：同一组件模型在目标硬件上成立粗估：5–10 人日，需按平台缺口重估

开始前的可行性门槛

先确定一块板及其资源 profile，不默认选 P4，不扩展到全部板型。逐项核对 WAMRC 目标、屏幕 / 触摸 / 字体、可用内存与最大连续块、音频输出、标准网络传输和可用 UTC 来源。已有网络连接可复用；Wi-Fi 配网流程不在本轮新增范围。

资源估算必须包含 Guest 线性内存、三类栈、Host 会话上下文、TLS、解码窗口、Scene / 字体 / 纹理、DMA、加载峰值和预留。若无法在目标板保持最少两个独立 Guest（前台＋音乐），应报告容量缺口并调整目标 / 应用容量，不以“Host 直接运行全部业务”替代多 Guest 验收。

实施任务

  1. 由 FirmwareApp 组合 AppManager、RTOS SessionRunner 和 scoped services；Host controller 为唯一状态写入者，每个存活 Guest 使用受控执行任务，组件不另开 Guest 线程。
  2. 将 AppRuntime 从单个 active_session 限制改为受预算的实例创建能力；审计任务本地上下文、WAMR 全局锁 / 分配器、全局缓存及共享执行器容量。
  3. 适配图形 / 输入 / DMA 归属与系统 Home；后台不持续绘制，停止时只排空本 owner。测量真实调用链总栈，而不是单独增加 task stack 掩盖大局部对象。
  4. 实现 MCU HTTP / TLS 平台适配与有界并发；沿用证书与主机名校验、请求 owner 和取消契约。选择与现有网络栈匹配的适配方式，不引入 Guest socket。
  5. 补齐 URL media、目标可用的 MP3 解码和固定大小流式 / 分块缓冲；Guest 只控制媒体句柄，Host 音频回调不下载、解码或分配。禁止搬用 PC 的整曲 128 MiB PCM 缓存。
  6. 新增平台依赖须固定版本、核查许可证并更新第三方声明；不复制或修改 WAMR 子模块来实现普通平台适配。
  7. 为音乐 / 天气定义 MCU 数据窗口、JSON / 歌单 / 图像上限和低内存 profile；按真实屏幕调整控件、字体、触摸区域和二维码显示，再更新 requirements。
  8. 接入 Host 时钟 / 任务 / 持久闹钟与音频焦点；数据适配分为 PC SQLite 与目标既有存储，不共享数据库实现。

代码位置：FirmwareApp、Host controller / Home、AppRuntime / AppSession / WAMR 包装层、Device 契约与目标 Platform 适配、既有 音频模块、内存模块、Guest 布局 / 容量配置和选定目标构建入口。WAMR 子模块源码仍不在本轮改动范围。

建议提交边界

D9.1：板级预算 / 中立接口 / Host 构建；D9.2：两 Guest 与 scoped graphics / input / audio；D9.3：HTTP / 媒体 / 低内存 HMI 与三应用场景。若新平台缺少成熟解码或 TLS 能力，应在 D9.1 评估后重估工时，而不是隐藏在最后的“联调”中。

验收与交付证据

  • 选定目标 build-host 与对应 Guest release Bundle 构建通过；有硬件验证记录，PC / QEMU 结果不能替代。
  • 至少前台 Guest 与音乐 Guest 共存；天气可按需唤醒，Clock Guest 退出后 Host 时间 / 闹钟仍有效。三个功能同时有效，不强制三个 Guest 永久驻留。
  • 在真实屏幕上完成扫码、歌单滚动、播放、Home 控制、天气更新、闹钟中断 / 正确恢复及用户正常关闭。
  • 测量任务最低空闲栈、Host / Guest 堆峰值、最大连续块、图形 / DMA 占用、解码窗口、切换延迟和音频 underrun；连续运行 30 分钟及 100 次正常切换 / 启停后无持续资源增长。
  • 容量不足在准入时明确拒绝并保留旧前台 / 音乐；有完整资源报告和目标 profile，不能仅展示“编译通过”。

回退边界：目标配置维持单槽能力直到板级验证通过；新多应用能力未通过的板型不默认启用。回退固件 / Guest 必须使用匹配版本；版本化持久登记保留读取 / 迁移策略。

Guest 线性内存每实例上限 16 MiB；总上限 64 MiB按模块与 profile 的较严格值；另计 WAMR 元数据、执行栈、原生栈、TLS、图形与解码。未知的共享堆成本不得假称已做硬配额。
HTTP每实例 2；Guest 总并发 8至少一个名额为关键 Service 预留；保证相应执行通道可用。市场 / Host 调度拥有独立预算。
ServiceRegistry由当前 16 按需显式扩为固定容量，初始建议 24D3 先完成服务 ID / 槽位审计、静态断言和内存账；端点不在实例内动态增删。
管理命令32 普通命令＋每实例关键控制邮箱普通命令可拒绝 BUSY；停止、退出和排空通知不得因普通队列满而丢失。
业务消息每 Service 8 条等待、单条 1 KiB邮箱仅为存活实例分配；另计在途票据、结果缓存及序列水位；不往 Event 中塞大 payload。
工作租约每 App 4；JOB 30 秒、Widget action 10 秒截止时间约束业务请求和租约，不是可抢占 Guest CPU 的证明。长工作拆分，消息完成只释放本 work_id。
Widget每 App 2、总计 8；快照 2 KiB；常规发布最多 1 次 / 秒schema、UTF-8、范围与版本独立校验；时钟 / 进度由 Host 推算，不要求 Guest 每帧发布。
媒体 / 闹钟1 个主媒体拥有者＋1 个 Host 闹钟输出Host 主音量不下放。焦点中断与用户暂停分别记录，不任意恢复旧媒体。
Job / Alarm 登记Job 总计 16、每 App 4；Alarm 总计 32、每 App 8计划按 AppId 持久管理；运行工作按 InstanceKey 管理；总容量不足明确拒绝。
图形 / 资源沿用现有固定表上限，拆出每 App 与全局上限D1 清单必须给出节点、纹理、字体、像素、上传量及帧率限额；未界定的全局资源不能直接开放给多个 Guest。

全局准入至少满足 Host 常驻预留＋各实例预留＋图形 / 媒体保留＋任务 / TLS / 加载峰值＋安全余量 ≤ 目标可用内存，同时检查内部 SRAM、PSRAM、DMA 与最大连续分配块，不能把它们视为一个可互换的大堆。

正常 handler 必须返回事件循环，Host 长操作异步化。保留现有 watchdog，但不据其超时配置宣称 AOT 可限时退出；不新增“无检查点纯循环也可安全强停”的验收项。

16合入、启用与回退

开工与每阶段流程

  1. D1 开始前保留当前已验证的 PC Host、音乐 Wasm / RV32 Bundle、fixture 和版本摘要到本地 build/，记录现有操作与资源基线。
  2. 每次先冻结该阶段协议和容量，再实现对应测试与代码；公开协议变更同步更新 SDK、reader、工具和示例。
  3. 按该阶段的 2–3 个提交边界完成变更；未完成能力由 profile 明确关闭，不维护旧页面副本。
  4. 运行受影响验证，完成阶段演示，记录通过 / 未运行 / 阻塞及原因。必要依赖缺失时不能把阶段标成完成。
  5. 更新实际已实现能力的 README 与架构基线，再合入阶段提交。设计提案不提前改成“已支持”。
  6. 阶段通过后进入下一次交付；依赖方只使用已落地、版本可协商的契约。

回退规则

首选同版本单槽 / 关闭未完成能力的配置回退，保留已经可读的配置与 Host 任务 / 闹钟。回退前先正常停止并排空新实例；尚未退出的实例不能被直接覆盖或复用。

requirements、任务和闹钟记录均版本化；旧 reader 对未知版本明确拒绝，不按旧布局解释。若必须退到不支持新闹钟的旧 Host，需先在新 Host 显式取消登记并备份配置，再更换匹配的 Host / Guest；不能承诺旧版本继续执行它不认识的提醒。

18最终完成条件

以下路径构成首版验收；每条都需要实际状态和资源证据，不能只做静态页面。

  1. 从 Home 进入音乐：完成登录或恢复可用账号，显示昵称 / 歌单并播放；返回 Home 后曲目和进度继续。
  2. 打开天气：天气成为唯一输入 / 显示目标，音乐继续；触发刷新后卡片发布新值，错误保留旧成功值。
  3. 关闭天气：天气实例局部退出，音乐不受影响；自动任务按用户停止策略处理，显式 Widget 刷新可重新启动。
  4. 销毁音乐页面：PlaybackService 与队列仍存在；再次进入复用 Guest 并重建 Activity，旧组件回调不能污染新页面。
  5. 设定并离开闹钟：Clock Guest 可停止，Host 时间持续显示；闹钟响铃获得焦点，结束后仅恢复有效播放意图。
  6. 停止音乐 App：媒体、请求、组件和资源只按其 owner 清理；Home、天气任务和 Host 闹钟继续。
  7. 耗尽容量：新请求明确被拒绝，旧前台和音乐保持；正常释放槽后可再次启动，不自动复用未退出的槽。
  8. 兼容与后端：旧官方 AOT 以前台 LegacyActivity 运行；新组件 Guest 在原生 / RV32 / 混合模式通过对应场景。
  9. 硬件：一块明确的 RTOS 目标通过资源报告、真实 HMI、网络、音频和组合运行；其余板型不默认标为支持。
本轮完成：正常路径的多应用功能闭环和一块硬件目标成立。下一轮独立目标：故障自动恢复、AOT 有界取消 / 计算预算，以及需要额外硬件支持的更强隔离。后续目标不反向作为这九次交付的隐含验收项。
