01 / START HERE

先理解 App 如何运行

MicroPixel App 是使用受限 C++23 编写的 Guest 程序，编译为 Wasm 或目标架构的 AOT。Host 负责显示、输入、音频、设备能力和应用生命周期；App 通过 guest/sdk/ 下的公共接口访问这些能力。普通 App 开发不需要修改固件、Host 或 ABI。

STEP 01创建项目app.json + C++ 源码
STEP 02声明能力显示、输入、服务、组件
STEP 03实现业务Model + 界面 + 事件
STEP 04构建运行PC 验证 / 目标设备实测
STEP 05测试发布版本、Bundle、商店资料
对象负责什么如何使用
Application一个 Guest 的能力入口和事件循环app.renderer()、app.network()、RunComponents()
Activity界面、输入和页面资源在生命周期回调中创建、更新和释放页面
AppService可独立于页面存在的业务工作网络请求、媒体、Job、Widget 发布等
ModelApp 自己定义的共享业务状态组件通过引用读取、修改，状态变化后触发界面更新
ComponentContext当前组件的应用访问、身份和生命周期请求context.app()、StartService()、Exit()
先选择目标和编程模式

当前 PC：新应用可采用 RunComponents()；简单前台应用也可继续使用 Run(handler)。当前 MCU：组合根尚未接入 Activity/Service，使用 Run(handler)。PC 上通过的组件应用不能据此认定已支持 MCU。详见第 13 章。

一个组件应用最多有一个 Activity 和一个 AppService。它们共享同一份 Guest 内存和一个串行事件循环。Service 没有额外 Guest 线程；业务回调也不会在执行中被另一个事件回调打断。

本指南以当前检出的源码为准。旧设计文档可能包含阶段性限制；涉及平台支持或 API 时，优先核对 SDK 头文件、当前 App 和可执行测试。

02 / PROJECT

准备环境并创建项目

2.1 确定工作目录与工具链

本页所有 python3 tools/… 和 bash tools/… 命令，均在仓库的 micropixel/ 根目录执行，即同时包含 guest/、firmware/、tools/ 的目录。已安装独立 SDK 时，使用 micropixel 替代 python3 tools/micropixel。

目标所需工具产物与运行方式
PC 原生 WasmPython 3、匹配的 WASI SDK；已构建的 PC HostWasm + *.pc.json，通过 PC Host 运行；这条路径无需 WAMRC
PC RV32 AOTWASI SDK、固定 fork 的 WAMRC、QEMU 与 RV32 runnerRISC-V Bundle，通过 PC Host 的 RV32 后端运行
MCU 真机WASI SDK、目标架构的固定 WAMRC、USB 连接依赖Wasm → AOT v6 → Bundle → 安装运行

WAMRC 必须来自项目锁定的 MicroPixel WAMR fork，生成 AOT v6。版本号相同的上游工具不能替代。普通 App 开发无需安装 ESP-IDF；修改 Host 固件时才进入固件构建流程。

Shell · 工具链配置示例
export WASI_SDK_PATH=/path/to/wasi-sdk
# 仅 AOT / 真机路径需要；替换为实际可执行文件。
export WAMRC=/path/to/micropixel-wamrc
python3 tools/micropixel --version

PC Host 已经构建完成时直接复用。首次搭建 PC 环境，按 PC README 执行 deps → configure → build；后续只改 App 时无需重建 Host。

2.2 生成项目

Shell · 在 micropixel/ 根目录执行
python3 tools/micropixel init guest/apps/counter \
  --app-id com.example.counter --title "Counter"
项目结构
guest/apps/counter/
├── app.json
└── src/
    └── main.cpp

init 创建的 Hello World 已能绘制页面并进入 Application::Run()。本指南后面的组件示例需要替换 app.json 和 src/main.cpp。已有清单时 init 拒绝覆盖；已有源码、没有清单时，可用 init . 扫描。

2.3 项目变大后如何拆文件

初期可把 Model 和组件放在一个 main.cpp 中。网络协议、解析或页面逻辑变复杂后，再拆为 model.hpp、app_activity.hpp/.cpp、app_service.hpp/.cpp、client.hpp/.cpp。每新增一个 .cpp，把它加入清单的 sources；头文件按正常 #include 使用。

App 只依赖 sdk/ 的公共 API。先查 SDK 能力目录，复用已有数学、字符串、JSON、手柄、布局、日历和音效工具。

03 / MANIFEST

把应用需求写进 app.json

清单既是构建输入，也是 Host 判断是否能接纳应用的依据。下面是第 6 章计数器使用的完整清单，保存为 guest/apps/counter/app.json。

app.json · 完整文件
{
  "schema_version": 1,
  "app_id": "com.example.counter",
  "version": "0.1.0",
  "threading": "none",
  "title": "Counter",
  "sources": ["src/main.cpp"],
  "requirements": {
    "schema_version": 2,
    "display": {
      "layouts": ["square"],
      "min_width": 720,
      "min_height": 720
    },
    "required": ["input.touch"],
    "optional": [],
    "any_of": [],
    "services": {
      "lifecycle": 65536,
      "graphics": 65536,
      "input": 65536,
      "timer": 65536,
      "storage": 65536
    },
    "components": {
      "activity": true,
      "service": true,
      "background": [],
      "widgets": 0
    }
  }
}
字段编写规则
schema_version顶层清单格式当前为 1；组件声明使用内层 requirements.schema_version: 2，两个版本号含义不同。
app_id稳定的应用身份，升级后保持不变。构建名称取 App ID 最后一段：com.example.counter 的名称为 counter。
title / version大厅显示名称与应用版本。版本使用规范 major.minor.patch，如 0.1.0；不使用前导零、预发布或构建后缀。
sources / threading相对项目目录列出所有 C++ 编译单元；当前标准 Guest 使用 "none"。不再使用旧的单数 source。
display如实声明支持的布局和最小逻辑尺寸；示例只验证 720×720 方屏。勾选其他布局前，需要实际实现和验证适配。
required / optional / any_of必需能力、可降级能力、每组至少一种的替代能力。示例必须触摸；不要把未实现降级的功能放入 optional。
services最低服务版本，用 (major << 16) | minor 编码：1.0 为 65536，1.1 为 65537，1.2 为 65538。
componentsActivity / Service 至少一种；与传给 RunComponents() 的指针一致。使用组件时必须要求 Lifecycle 1.0。
background / widgets后台类型只能为 media、task，且要求 Service；widgets 当前声明 0–2 个，也要求 Service 与 Widget 服务。

计数器的 background: [] 表示没有申请后台工作类型。它用 Service 展示业务拆分，返回 Home 后允许整个实例挂起；定时器不会变成持续后台计时器。

使用中文系统字体时添加 "system_font": "zh-CN"，并确认目标 Host 的字体支持。网络、媒体、消息、Job 等服务版本按实际调用的 API 声明，可对照对应 SDK 头文件注释和现有应用清单。

04 / COMPONENTS

分清状态、页面与业务的生命周期

Application · 唯一事件循环 RunComponents()
Activity页面、输入、Scene、页面 Timer
AppService请求、媒体、Job、消息、业务 Timer
共享 Model · 业务数据 / 设置 / 缓存 / revision
组件通过公共 SDK 调用 Host；不直接访问驱动或 AppManager

4.1 Model 的寿命由你持有它的位置决定

在 main() 中创建 Model，把引用传给两个组件，并让它存活到 RunComponents() 返回。页面资源销毁后，Model 仍然存在。Service 只依赖 Model、业务对象和必要的应用能力，避免保存 Activity 或控件指针。

页面需要知道数据变化时，可以在 Model 中维护递增的 revision。业务更新后递增；Activity 在自己的定时器或其他更新入口比较版本，仅在变化时重绘。这里是同一串行循环内的普通引用访问，无需引入线程同步。

4.2 Activity 回调应该做什么

OnCreate→OnResume→OnStop→OnResume / OnDestroy
回调建议职责容易混淆的点
OnCreate创建 Scene、控件、纹理、页面定时器，显示首帧同一个组件对象可能再次收到此回调；重建本次页面所需资源。
OnResume同步最新 Model、恢复输入状态、按需重绘从 Home 回来可能只恢复已有页面，通常不会重新执行 main。
OnEvent处理当前组件的输入、Timer 和其他业务事件按来源判断事件；不能认为任何 Timer 都是自己的 Timer。
OnStop取消按下状态、拖拽、输入焦点等前台交互Activity 停止/隐藏保留页面资源；不同于整个 App 退出。
OnDestroy释放 Scene、页面 Timer、纹理等 RAII 对象，清空节点引用生命周期销毁不等于 C++ 对象析构；对象仍由 main 持有。

4.3 Service 的启动、停止与后台资格

OnStart 创建业务资源、恢复必要状态或注册工作计划；OnEvent 推进请求和任务；OnStop 取消请求、释放 Timer/媒体，并做有界的状态保存。停止后再次启动，仍可能使用同一个 C++ 对象，所以每个代次都应重新初始化临时句柄和工作票据。

RunComponents(&activity, &service) 默认请求启动 Service；第三个参数为 false 时，初始不主动启动，之后可通过 context.StartService() 请求。RunComponents(&activity) 可用于只有页面的应用；清单也要把 service 设为 false。

三个不同的操作

DestroyActivity() 销毁页面资源域，AppModel 和 Service 可继续存在；StopService() 结束当前 Service 代次；Exit() 请求结束整个 App。组件生命周期请求由 Host 和 Runtime 推进，并非在调用表达式中同步执行所有回调。

用户显式打开应用才创建或恢复 Activity。Host 的后台 Job 冷启动可能只启动 Service；业务初始化应放在 Model 或 Service 的合适位置，不能依赖 Activity 已经执行过 OnCreate。

05 / OWNERSHIP

ComponentContext 与资源归属

ComponentContext 定义于 guest/sdk/components.hpp。它让回调访问同一个 Application，并携带当前组件的 token。token 表示实例内的组件身份与代次；不能把它当作跨 App 的全局地址。

接口作用
app()取得 const Application&，调用 renderer、network、storage、timers 等能力。
token()查询本次组件代次身份，可用于日志诊断。
StartService() / StopService()请求启动或停止 Service。
CreateActivity() / DestroyActivity()请求创建或销毁 Activity；不重启整个 Guest main。
Exit() / Status()请求结束 App；查询组件状态、token 与资源记录数量。
WithScope(function)在函数执行期间显式选择这个 Context 的资源域，结束后恢复原域。

5.1 资源在创建时绑定组件域

Runtime 调用组件回调前，自动选中当前组件域。Activity 回调中创建的 Timer、纹理等属于 Activity；Service 回调中创建的请求、Timer 等属于 Service。绑定看的是创建时所在的域，而非对象最终放在哪个 C++ 成员变量里。

因此，把 Activity 回调中打开的 HTTP 请求 move 到 Service 成员中，并不能把它变为 Service 资源。需要在 Service 回调里创建，或在保存且仍有效的 Service Context 上通过 WithScope 显式执行。主事件循环外、未选中组件域时创建的共享资源归 App 域，应明确其整个 App 的寿命。

5.2 Context 与保存的引用

不要保存回调参数 ComponentContext& 的地址：该 Context 是分发回调时的临时对象。确需保存时，按值保存 Context；其中的 Application 引用必须继续有效，而且原组件代次不能已经结束。日常应用优先在当前回调内使用它。

保存 &context.app() 指向的是 main 中的 Application，天气 Service 就这样做。但保存 Application 指针不等于保存资源域：之后从另一个组件调用共享 helper 时，创建资源仍遵循当前域。

5.3 RAII 对象与 Host 回收

Timer、Texture、HttpRequest 等通常为 move-only 资源代理。用成员对象或 std::optional<T> 持有，在 OnDestroy / OnStop 中主动释放。Host 的组件域回收用于兜底，不替代应用清理 C++ 状态。

C++ · 组件成员示意
std::optional<Timer> timer_;
std::optional<Scene> scene_;

void OnDestroy(ComponentContext&) override {
    timer_.reset();
    scene_.reset();
}

Scene 销毁后，其 Label/Sprite 节点引用失效；重新创建页面时重新赋值。Service view（例如 auto renderer = app.renderer()）只是轻量能力入口，保存它不会自动延长其创建资源的寿命。

06 / COMPLETE EXAMPLE

写一个完整的 Activity + Service App

这个计数器使用两份职责清晰的组件：Service 每秒更新共享 Model；Activity 读取 Model，显示数值并处理 Reset 按钮。退出整个 App 时保存，下一次启动读取。它没有后台常驻或时钟语义：返回 Home 后允许挂起。

  1. 准备清单使用第 3 章完整 app.json，App ID 为 com.example.counter。
  2. 替换源码把下面代码整体保存为 guest/apps/counter/src/main.cpp。
  3. 编译运行执行本章末尾两条命令，打开页面后观察数值增长并点击 Reset。
src/main.cpp · 完整文件，可整体复制
// SPDX-License-Identifier: Apache-2.0
#include <optional>

#include "sdk/micropixel.hpp"

namespace {
using namespace micropixel;
using namespace micropixel::literals;

struct Model {
    uint32_t count{}, revision{};
};

class CounterService final : public AppService {
   public:
    explicit CounterService(Model& model) : model_(model) {}

    void OnStart(ComponentContext& context) override {
        timer_.emplace(context.app().timers().Every(1_s).value());
        context.app().log().Info("COUNTER service started");
    }

    void OnEvent(ComponentContext& context, const Event& event) override {
        if (!timer_) return;
        const auto* tick = event.TimerFrom(*timer_);
        if (!tick) return;
        model_.count += 1U + tick->missed_count();
        ++model_.revision;
        FixedString<64> text;
        text.Append("COUNTER value=");
        text.AppendUint(model_.count);
        context.app().log().Info(text.c_str());
    }

    void OnStop(ComponentContext& context) override {
        timer_.reset();
        auto saved = context.app().storage().SetU32("counter", model_.count);
        if (!saved) context.app().log().Info("COUNTER save failed");
    }

   private:
    Model& model_;
    std::optional<Timer> timer_;
};

class CounterActivity final : public Activity {
   public:
    explicit CounterActivity(Model& model) : model_(model) {}

    void OnCreate(ComponentContext& context) override {
        const auto& app = context.app();
        scene_.emplace(app.renderer().CreateScene(Color::Rgb(244, 246, 242)).value());
        (void)scene_->CreateLabel({48, 48}, "My first MicroPixel App", Color::Black()).value();
        value_ = scene_->CreateLabel({48, 160}, "0", Color::Black(), SystemFont::kTitle).value();
        (void)scene_->CreateShape({48, 280, 260, 88}, Color::Rgb(208, 224, 209)).value();
        (void)scene_->CreateLabel({80, 306}, "Reset", Color::Black()).value();
        (void)scene_->CreateLabel({48, 410}, "Home / F1: return to Home", Color::Black()).value();
        reset_.SetBounds({48, 280, 260, 88});
        timer_.emplace(app.timers().Every(100_ms).value());
        Draw(app);
        app.log().Info("COUNTER activity created");
    }

    void OnResume(ComponentContext& context) override {
        reset_.Reset();
        Draw(context.app());
    }

    void OnEvent(ComponentContext& context, const Event& event) override {
        if (const auto* touch = event.touch()) {
            if (reset_.OnTouch(*touch).clicked) {
                model_.count = 0;
                ++model_.revision;
                Draw(context.app());
            }
        }
        if (timer_ && event.TimerFrom(*timer_) && seen_ != model_.revision) Draw(context.app());
    }

    void OnStop(ComponentContext&) override { reset_.Reset(); }

    void OnDestroy(ComponentContext&) override {
        timer_.reset();
        value_ = LabelNode{};
        scene_.reset();
    }

   private:
    void Draw(const Application& app) {
        if (!scene_) return;
        FixedString<32> text;
        text.AppendUint(model_.count);
        value_.SetText(text.c_str());
        app.renderer().Present(*scene_).value();
        seen_ = model_.revision;
    }

    Model& model_;
    std::optional<Scene> scene_;
    std::optional<Timer> timer_;
    LabelNode value_;
    ui::Button reset_;
    uint32_t seen_{};
};
}  // namespace

int main() {
    Application app;
    app.renderer()
        .ConfigureDisplay({.logical_size = {720, 720}, .scale_mode = DisplayScaleMode::kAspectFit})
        .value();
    Model model;
    model.count = app.storage().GetU32Or("counter", 0);
    CounterActivity activity(model);
    CounterService service(model);
    app.RunComponents(&activity, &service);
    return 0;
}
Shell · 原生 PC 运行
bash tools/pc.sh guest guest/apps/counter
bash tools/pc.sh run --autostart build/pc-apps/counter/counter.pc.json

代码中的六个设计点

  1. main 只负责组装。创建 Application、一次性配置逻辑画布、恢复 Model、创建组件，然后进入唯一事件循环。
  2. Model 在组件之外。销毁页面资源不会丢失数值；真正结束 Guest 后，内存 Model 才随进程生命周期结束。
  3. 两份 Timer 各有归属。Service 的 1 秒 Timer 更新业务，Activity 的 100 毫秒 Timer 检查 revision。事件通过各自句柄匹配。
  4. 重绘先改节点，再 Present。LabelNode::SetText() 修改 Guest 场景，Present() 提交到 Host。
  5. 隐藏与销毁分开。OnStop 清除触摸状态；OnDestroy 释放 Scene 与页面 Timer。重建页面重新绑定节点。
  6. 保存不是每帧操作。示例在 Service 停止时写入一个整数。异常终止或突然断电可能丢失未保存值；重要状态应在用户确认等业务边界及时提交。

missed_count() 用于补回同一周期 Timer 合并的通知。真实运动、动画和模拟应使用 tick->delta() 推进；跨挂起、断电或后台的真实时间需求应使用 Host wall time / Job / Alarm。

把示例改成只有页面的 App

删除 CounterService，把更新逻辑放入 Activity 自己的 Timer；入口改成 app.RunComponents(&activity)；清单中 components.service 改为 false。只在业务确实需要独立生命周期时引入 Service。

07 / UI & INPUT

创建界面、适配布局并处理输入

7.1 先选图形更新模型

场景推荐接口工作方式
页面、按钮、文字、精灵Scene + ui::*保留节点，修改属性后 Present；适合大多数工具类 App。
整帧光栅、射线投射、批量绘制HostSurface + RasterDrawList向 Host 缓冲区提交绘制列表。
必须直接逐像素生成的画面GuestSurfaceGuest 写线性内存像素；成本和平台支持需单独确认。

Scene 的节点工厂返回 Result<Node>。创建 Label、Shape、Sprite 后把需更新的节点句柄保存在 Activity；静态节点无需反复创建。容器形成局部坐标与子树边界，跨容器操作时按 SDK 的坐标转换约定处理。

重复页面结构使用公共组件

SDK 已提供 AppBar（标题与动作）、SegmentedControl（选项组）、VirtualList（固定行高列表和网格）、ContentStateView（加载、空与错误提示）和 Theme。它们在 Guest 组合 Scene，避免各 App 重写行池、触摸仲裁和标题布局。详见组件设计与接口契约。Activity 停止时 CancelInput，销毁时先释放组件再释放 Scene；页面汇总 changed 后 Present。

7.2 配置逻辑画布的时机

在读取布局信息、创建场景、加载纹理或使用触摸转换前，调用一次 ConfigureDisplay()。配置会冻结；不能把它当成每次恢复页面都能重新设置的操作。计数器把它放在 main 中，Activity 的每次 OnCreate 只重建 Scene。

缩放模式含义适合
kNative默认模式，逻辑坐标等于屏幕像素，logical_size 留空按实际 RendererInfo 自适应布局
kAspectFit完整显示设计画布，必要时留边固定设计尺寸、希望内容完整可见
kAspectFill等比铺满，可能裁切允许边缘裁切的视觉内容
kExpand容纳设计尺寸并扩展逻辑画布利用不同宽高比增加可用区域

输入的 Touch 坐标与逻辑画布匹配，通常不用自己乘屏幕缩放比例。留边区域的触摸可能在画布外，应正常做矩形命中检查。系统字体使用语义字号，物理字号由 Host 决定，不保证与设计画布等比例放大；关键排版应测量文本并检查安全区域。

7.3 文字、按钮与列表

优先使用 SDK 的 ui::TextButton、FlexContainer、GridContainer、ScrollView 等控件。完全自定义外观时，ui::Button 只维护触摸状态，由 App 自行绘制。不要只检查一次抬起坐标：还要正确处理按下捕获、移出、Cancel 和组件失焦。

长文本用 sdk/ui/wrap_text.hpp 的有界 UTF-8 折行工具，传入文本测量回调；数字格式化可用 FixedString。面板应用可以显式包含 sdk/ui/panel.hpp、numerals.hpp、material_icons.hpp 等现有工具。

7.4 游戏输入与系统交互

游戏使用 app.gamepad() 配置需要的逻辑控件，逐帧读取状态；Runtime 统一处理触摸、按键和支持的模拟轴。不要再次手动向同一 pad 转发事件。菜单需要接收触摸时按契约禁用手柄。Home、系统手势、设备主音量和系统浮层由 Host 负责。

08 / ASYNC WORK

用事件推进定时器和网络请求

8.1 让每次回调及时返回

业务按“开始工作 → 返回事件循环 → 后续事件检查进度 → 完成或取消”的顺序推进。不要在回调里用忙循环等网络完成，也不要使用线程、mutex、POSIX socket 或系统 sleep。Guest 是受限运行环境，常用 STL 容器可用，但不是完整 WASI/POSIX。

Timers::Every() 和 After() 返回 RAII Timer。通过 event.TimerFrom(timer) 匹配来源；周期事件可能合并，动画使用 delta()，遗漏次数通过 missed_count() 观察。Timer 取消释放句柄，后续需要调度时重新创建。

8.2 HTTP 客户端的最小状态机

app.network().Exchange() 支持显式处理 HTTP 状态与跳转。Network 1.2 的 receive_timeout_ms 为接收空闲超时，不是整个业务 Job 的总预算。请求启动、查询、读取都可能失败，要分别处理。

Idle→Pending→Complete / Failed→Close

下面的客户端可作为 Service 成员；Start 在 Service 域调用，Service Timer 驱动 Poll。示例要求 Network 1.2（清单中 network: 65538）。它只处理 HTTP 200，不自动跟随重定向。

C++ · 有界 HTTP 客户端
// SPDX-License-Identifier: Apache-2.0
#pragma once
#include <string>
#include <utility>
#include "sdk/micropixel.hpp"

class TextClient final {
   public:
    bool Start(const micropixel::Application& app, std::string_view url) {
        Cancel();
        auto opened = app.network().Exchange(
            micropixel::HttpMethod::kGet, url, {}, {}, kLimit,
            {.receive_timeout_ms = 10000});
        if (!opened) return false;
        request_ = std::move(*opened);
        return true;
    }

    // 0: pending; 1: success; -1: failed.
    int Poll(std::string& output) {
        if (!request_.valid()) return -1;
        auto state = request_.State();
        if (!state) return -1;
        if (state->phase == micropixel::HttpPhase::kPending) return 0;
        if (state->phase != micropixel::HttpPhase::kComplete ||
            !state->body_length || state->body_length > kLimit) return -1;
        auto metadata = request_.Metadata();
        if (!metadata || metadata->status_code != 200) return -1;
        std::string next(state->body_length, '\0');
        auto read = request_.Read(0, {
            reinterpret_cast<uint8_t*>(next.data()), next.size()});
        if (!read || *read != next.size()) return -1;
        output = std::move(next);
        return 1;
    }

    void Cancel() { request_.Close(); }

   private:
    static constexpr uint32_t kLimit = 16384;
    micropixel::HttpRequest request_;
};

在 Service OnEvent 的 Timer 分支调用 client.Poll(body)：返回 0 等待下一个事件，返回 1 后解析并提交 Model，返回 -1 显示失败并保留旧缓存。无论成功或失败，完成路径调用 Cancel() 释放请求；Service OnStop 同样取消。

8.3 先验证，再提交结果

使用 sdk/json.hpp 的 Json，按业务设置 token 上限。校验 HTTP 状态、响应大小、JSON 结构、字段类型、数值范围和请求所对应的业务身份。先解析到临时结果，全部验证通过后才替换 Model 的最后成功值。

Json 持有输入文本的 view，解析与字段读取期间原字符串必须保持有效。请求期间用户切换城市、账户或查询条件时，使用快照或 revision 检查，防止旧请求完成后覆盖新页面数据。天气 App 就在提交前比较请求城市与当前城市。

8.4 Result 与错误边界

可恢复错误检查 Result 后进入回退逻辑；只有确实无法继续的初始化失败才直接 .value() 或 Assert/Panic。读取错误状态的 value() 会 trap；禁止用 try/catch 处理，Guest 没有异常支持。析构与清理只做 best-effort，不能依赖它们执行长操作。

09 / HOST SCHEDULING

后台工作、Widget 与消息

Service 让业务与页面生命周期分离；后台执行资格由 Host 决定。默认 PC Home 根据前台状态、媒体、活动 Job 和待处理消息等安排运行或挂起。声明 background: ["task"] 不代表任意 Timer 永久运行。

9.1 用 Job 表达有限后台工作

周期刷新、定期拉取数据应注册 Host Job 计划。Host 可以恢复挂起实例，或启动只有 Service 的新实例；这不会自动把应用切到前台。Guest Timer 随挂起冻结，Host Job 的时限继续推进。

C++ · 注册 15 分钟周期计划，放在合适的 Service 初始化入口
auto now = context.app().jobs().Now();
if (now && now->valid) {
    auto registered = context.app().jobs().Register({
        .id = 1,
        .interval_seconds = 900,
        .deadline_ms = 20000,
        .next_utc = now->utc
    });
    if (!registered) context.app().log().Info("Job registration failed");
}
  1. 声明与登记requirements 中声明 job: 65536、Lifecycle、Service 和后台 task；按业务时机注册计划。没有有效 wall time 时，明确等待、提示或稍后重试。
  2. 领取工作收到 event.job() 后检查是否为取消通知；正常工作先调用 jobs().Enter(ticket)，成功后才发起本次业务。
  3. 推进与完成异步处理请求，成功、失败和取消路径都收束到同一个完成函数，最终调用 jobs().Complete(ticket)。
  4. 尊重预算与代次超时取消当前工作；旧票据不能清理新的请求。计划可持久保存，work ticket 只对当前启动有效。

当前周期范围为 60–86400 秒，工作预算为 1–60 秒；天气默认每 900 秒刷新、20 秒预算。用户显式 Stop 后，Host 阻止自动唤醒；重新打开应用或执行允许的 Home 刷新操作可以重新激活。详细限制见 D6 后台工作契约。

9.2 Widget 发布的是数据快照

Home 的卡片由 Host 绘制。Service 调用 app.widgets().Publish(id, WidgetData) 提交标题、摘要、更新时间、有效期及模板字段，不自己绘制 Home UI。使用稳定的 Widget ID；失败时保留最后成功的数据，同时设置失败标记。

清单中声明实际 Widget 数量并要求 Widget 服务。例如天气使用 WidgetTemplate::kWeather，更新温度、天气代码、城市和数据有效时间。页面可以销毁，Home 快照仍由 Host 管理。

9.3 消息表达操作请求

同一实例内的状态共享可以直接通过 Model；需要由 Host 路由、从 Home 操作或跨 App 调用时使用 Messages。发送方调用 Send()，接收 Service 收到 MessageEvent 后 Read(ticket)，验证操作类型和 payload，处理完成后 Ack(ticket, status)。

共享的 Model 不应因等待消息回复而阻塞事件循环。跨 App 冷启动默认禁止，需要 Message 1.1 和接收方显式允许；仅使用 App ID 或实例地址不等于获得启动权限。同一个非零 request_id 的重试必须保持相同内容，新操作使用新的序号。

9.4 Alarm 与 Timer / Job 的区别

页面动画用 Timer；有预算的数据刷新用 Job；需要由 Host 持久管理、应用停止后仍可到点提醒的闹钟用 Alarm。不要用 Guest Timer 模拟 durable alarm。可参考 clock-alarm 与 alarms.hpp，不要假设普通应用有修改系统时间等可信时钟权限。

10 / APP CAPABILITIES

保存状态、声明资源并播放音频

10.1 持久化与重建

使用 app.storage() 访问按 App ID 隔离的 KV。设置、最后选择、最高分和最后成功缓存可以保存；Scene、资源句柄、组件 token 和 Job ticket 属于运行时代次，不持久保存。

C++ · 读取默认值并检查保存结果
uint32_t city = app.storage().GetU32Or("city", 0);
auto saved = app.storage().SetU32("city", city);
if (!saved) app.log().Info("Saving city failed");

key 最多 15 个 UTF-8 字节，单 value 协议上限 4096 字节。总容量和 key 数量由 Host 策略限制，PC 与 MCU 默认配额不同；不要把配额视为已预留的物理空间。结构体缓存增加版本和长度检查；字段变化时迁移或重置，跨版本稳定格式优先显式序列化。

写入在 Host 提交后返回，会影响事件处理时间；只在设置确认、业务完成、检查点或有界停止等必要时机保存。同 App ID 覆盖安装保留私有状态；显式卸载会清理。

10.2 素材与资源 ID

运行时素材通过项目 asset_manifest 声明，由构建工具生成资源包和绑定。使用生成的 AssetId 加载纹理和字体，不手写资源目录数字，也不依赖任意文件系统路径。

加载纹理时就决定存储比例；仅把 Sprite 目标矩形画小，不会减少纹理的解码内存。Scene / Surface 混用时按 SDK 的逻辑坐标、缓冲坐标和纹理比例契约处理。参考 sdk-demo 清单、素材清单 与 SDK 图形说明。

10.3 音频与设备能力

短音效参数写在 audio/sfx.json，复用生成 profile 与 ToneSequencer；片段播放用 AudioClip/Playback，连续合成用 PcmStream，URL 媒体按目标平台能力选择。设备主音量由 Host 管理，App 不再添加一层全局主音量。

传感器通过 app.devices() 发现并用 typed Sensors API 打开；不要按板名或物理设备名硬编码路由。GPIO、振动、音频、传感器需求同时体现在清单和运行时错误处理里；可选能力缺失时提供正常回退。

10.4 内存与受限 C++23

可使用已验证的 array/span/string_view、optional、vector/string、unique_ptr 等。限制响应长度、JSON token 数量、列表缓存和临时工作区，避免无界增长。线性内存与 Host 图形内存有各自限制；PC 余量不能推导 MCU 的性能或可用内存。

不使用 exception、RTTI、线程、mutex、filesystem、原生 socket 或自行新增 WASI import。能力调用走 SDK；SDK 到 wire 的转换集中在 Guest Runtime，应用无需触碰 guest/abi/。

11 / CASE STUDY

沿着天气 App 读一遍真实业务

组装入口：main.cpp；共享状态：weather_model.hpp；页面：weather_activity.hpp；后台刷新：weather_service.hpp；网络客户端：weather_client.hpp；组件要求：app.json。

C++ · 天气 App 的 main
int main() {
    micropixel::Application app;
    weather::Model model(app);
    weather::WeatherActivity page(model);
    weather::WeatherService service(model);
    app.RunComponents(&page, &service);
    return 0;
}

11.1 初始化：先恢复可用内容

Model 从私有 KV 恢复城市与最后成功 Reading，检查版本、存储长度和城市索引。Service 启动 100 毫秒 Timer，发布已有 Widget 快照，wall time 有效时登记 Job。Activity 创建 Scene、天气图标、数字和城市选择页，先绘制缓存，无需等待首次网络成功。

11.2 手动刷新：从页面动作到 Service

  1. 页面识别操作刷新按钮通过 SDK 触摸状态判断点击；城市切换先保存选择并清理不适用的旧 Reading。
  2. 发送刷新消息Activity 向本 App ID 发送 AppAction::kRefresh；Service 读取消息并检查是否已有刷新消息正在处理。
  3. 登记单次 JobService 使用有效 Host 时间创建本次有限工作，由 JobEvent 提供票据。
  4. 进入工作并启动请求Service 调用 jobs().Enter(ticket)，记录本次城市、设置 busy、增加 revision，然后启动客户端。
  5. 后续 Timer 推进WeatherClient::Poll() 查询状态，校验 HTTP 200、16 KiB 长度限制和 JSON 字段。
  6. 统一完成成功且城市未变化时写入 Reading、保存；完成函数关闭请求、更新失败状态、发布 Widget、Complete 工作、Ack 消息，并处理排队工作。

11.3 页面怎样看到新数据

Model 的 revision 随业务变化增加。Activity 的 250 毫秒 Timer 发现版本不同后调用 Draw()，更新现有节点并 Present；OnResume() 也立即按当前 Model 绘制。网络业务通过共享 Model 连接到 UI，Service 不直接操作页面节点。

11.4 失败、取消和旧请求

客户端把解析结果放入临时 Reading；网络错误、坏 JSON、超时和刷新期间城市变化都不会提交旧结果。取消事件只清理匹配的工作票据；完成路径保留最后成功值，并更新 failed 状态供页面与 Widget 展示。

编写自己的数据型 App 时，可以沿用这条链路，把城市替换成文章、账户或查询参数。先建立业务身份快照，再异步获取、验证、提交和通知界面。

构建、运行并定位问题

13 / COMPATIBILITY

编写当前 MCU 可运行的应用

当前 MCU 组合根未注册组件 Lifecycle 能力，requirements v2 组件包不会因此自动兼容。需要今天就在 MCU 运行时，用 Application::Run(handler) 管理前台页面与业务，使用不含 components 的 requirements v1 清单。

C++ · Run() 完整最小应用
// SPDX-License-Identifier: Apache-2.0
#include "sdk/micropixel.hpp"

int main() {
    micropixel::Application app;
    auto scene = app.renderer().CreateScene(micropixel::Color::Black()).value();
    (void)scene.CreateLabel({24, 24}, "Hello, World!", micropixel::Color::White()).value();
    app.renderer().Present(scene).value();

    app.Run([&](const micropixel::Event& event) {
        if (event.type() == micropixel::EventType::kResume)
            app.renderer().Present(scene).value();
        return micropixel::EventResult::kContinue;
    });
    return 0;
}

配置 sources 指向这个文件；清单内层 requirements.schema_version 使用 1，删除 components 和不需要的 Lifecycle 服务要求。显示布局、字体和其他能力仍需与实际实现一致，可从 init 生成的清单开始调整。

13.1 连接设备运行

Shell · 仅对已适配当前 MCU 的项目使用
python3 tools/micropixel --transport usb device status
python3 tools/micropixel --transport usb run path/to/your-app

# 构建、安装、启动，完成后不跟随日志
python3 tools/micropixel --transport usb run path/to/your-app --no-follow

连接设备的 run 会识别芯片并选择目标 AOT。默认跟随日志，Ctrl-C 结束日志跟随，设备 App 继续运行。仅安装 App 不需要刷完整固件；串口不能同时被多个工具占用。

13.2 Run() 的停止与恢复

Run() 的 Timer、输入和完成事件进入同一个 handler。恢复原 Session 时收到 Resume，不重新调用 main；返回 EventResult::kExit 可以主动退出。Host Stop 到来后按 SDK 约定做有界保存与清理，不能在停止回调里进行长网络操作。

MCU 图形、音频、传感器、内存和网络能力必须在选定板型上实测。不要因 PC 有 URL 媒体、文本输入或宽松内存，就把这些能力默认为所有 MCU 可用。真机操作前阅读构建与烧录指南。

14 / VALIDATION & RELEASE

把“能运行”推进到“可交付”

14.1 先验证 App 自己的行为

  • 全新状态能显示首帧；没有数据时有清晰的等待或空状态。
  • 核心输入路径可用，拖出按钮、取消触摸和失焦后没有残留按下状态。
  • Home 隐藏与恢复正确；Activity 销毁后重建能够使用仍然有效的 Model。
  • Service 独立启动和停止安全；异步取消后迟到结果不会写回新一轮业务。
  • 网络失败、坏数据、超时与重复操作保留可用状态，并允许重试。
  • Job 的成功、失败和取消路径都 Complete；消息都有对应 Ack。
  • 设置保存与重启恢复符合预期，数据版本迁移和存储失败有处理。
  • 只声明实际支持并验证的布局、能力和目标平台。

14.2 按改动范围选择回归

纯 App 改动先构建该 App 并运行相关业务检查；解析器和状态迁移可以用确定性输入验证。修改 SDK/ABI 时增加相关 conformance；修改 Host 时通过仓库 wrapper 运行相关 Host 检查。不要把 PC 编译通过当作协议、生命周期和硬件验证全部完成。

Shell · 修改框架时按需选择，普通 App 不必全部执行
bash tools/tests/test_firmware_host.sh --app-framework
bash tools/tests/test_firmware_host.sh --pc --components
bash tools/tests/test_firmware_host.sh --pc --jobs

测试入口与覆盖见 Guest tests 和对应 App 的 README。Host 测试只通过 tools/tests/test_firmware_host.sh 运行，避免自行拼接编译命令。

14.3 打包与发布的边界

PC 的 *.pc.json 是本地运行描述符，不是商店 Bundle。离线 package 必须显式选择 AOT target；连接设备的 run / app install 自动选择目标。包格式、运行后端和目标平台支持是三个需要分别确认的条件。

Shell · 仅对目标平台兼容的项目使用
python3 tools/micropixel package path/to/your-app \
  --aot-target riscv32-ilp32f

# 发布前本地正式构建与校验
python3 tools/micropixel publish path/to/your-app --dry-run
当前组件教程不直接等于 MCU 商店发布模板

当前 publish 流程按 RISC-V 和 Xtensa 两种 MCU 架构构建、校验并上传 Bundle。计数器采用的组件模式目前用于 PC；进入该发布流程前，必须先具备目标 Host 支持，或把应用实现为当前 MCU 可用的模式。

正式发布时提升规范版本，准备至少两张不同的真实运行画面、简短介绍、详细操作说明和准确的设备需求。之后执行 GitHub 开发者登录与 publish；成功后在返回的编辑页填写和上传商店资料。截图和说明不会自动随项目文件上传。

Shell · 确认目标兼容并完成实测后再执行
python3 tools/micropixel auth github
python3 tools/micropixel publish path/to/your-app

同版本同架构不能替换成不同 Bundle；更新二进制时提升版本。更完整的素材限制、工具链设置与发布顺序见 发布应用。

15 / TROUBLESHOOTING

按现象定位常见问题

现象先检查什么
Activity / AppService 类型不完整完整定义在 sdk/components.hpp；只包含 application.hpp 得到的是前向声明。也可包含总入口 sdk/micropixel.hpp。
组件包被拒绝requirements 内层版本 2、Lifecycle 1.0、组件声明与 RunComponents 参数；目标是否为当前支持组件的 Host。
找不到生成的 pc.json构建名称来自 App ID 最后一段；区分 build/pc-apps 与 build/pc-rv32-apps，查看命令输出的 PC app ready 路径。
只看到空白或旧画面Scene 是否已创建；修改节点后是否 Present；提交是否失败；启动是否实际打开目标 App。
恢复页面时报显示配置错误ConfigureDisplay 是否在布局被冻结后再次执行；移到最早的一次性初始化位置。
Service 的请求随页面销毁被取消请求是否实际在 Activity 域创建；move 到 Service 成员不会改变资源归属。
Timer 没触发或收到错的 TimerRAII 对象是否已析构/Reset，是否使用 TimerFrom 匹配，组件或实例是否已经挂起。
Home 后 Service 不再执行当前后台资格与 Host 策略；普通 task 声明不保证常驻，周期业务应使用 Job。
换城市后显示旧请求结果是否记录发起请求时的业务身份，并在提交时再次核对；取消和迟到结果是否按代次处理。
HTTP 完成却解析失败HTTP 状态、空响应、长度上限、Read 返回字节数、JSON token 限制，以及输入字符串寿命。
出现 Trap / Panic先看原始日志定位调用；错误 Result 上的 value()、OOM、无效节点和无界计算都可能导致结束。
中文缺字或文字溢出system_font、Host 字体、测量结果与实际布局；语义字号不保证按画布等比例缩放。
新增 cpp 的函数链接不到该编译单元是否加入 app.json 的 sources；头文件声明与实现签名是否一致。
启动后读到旧设置同 App ID 升级会保留 KV；诊断时使用独立数据目录，测试版本迁移，而非假定重编就是全新安装。

需要重新组织代码时，按寿命判断

随页面消失的控件和临时输入状态放 Activity；页面重建仍要保留的业务状态放 Model；页面之外仍有意义的请求、播放和有限工作放 Service；需要跨进程启动或长期保存的计划交给 Host 的 Job / Alarm 等能力。
