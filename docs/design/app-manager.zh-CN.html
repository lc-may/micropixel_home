01目标与最小设计

当前实现仍是一个 Guest Session：PC Home 与市场由 Host 承载，音乐可以在这两个系统页面后继续执行；启动另一 Guest 会停止旧会话。本文提出下一阶段的架构，不表示现有运行程序已经具备多会话能力。基线见 PC Home 设计。

分阶段落地见 九次交付实施计划。首轮聚焦正常路径的多应用与 HMI，故障恢复及 AOT 强停补强后置；本文保留较完整的长期架构契约。

最小模型：一个 AppId 对应至多一个 Guest；App 可含 0–1 个 Activity、0–1 个 App Service。组件有各自生命周期，共用实例而不创建 Guest 线程。多个 App 的 Guest 独立运行，屏幕至多属于一个 Activity。

实例生命周期

5 种状态

STOPPED、STARTING、RUNNING、SUSPENDED、STOPPING。

Activity 与 Service

独立的组件生命周期

Activity 停止或销毁不等于 Service 停止；组件也不等于独立 Guest。

后台执行资格

有原因、有期限、有归属

音乐播放、有限任务和 Widget 操作可获得执行租约；注册 Widget 本身不保证常驻。

应用用户要求最小实现Home 显示
天气自动更新，不影响音乐WeatherActivity 展示详情；WeatherService 被 Host 定时唤醒，执行有期限的刷新并发布卡片城市、温度、描述、最后成功更新时间
时钟闹钟时间持续显示，页面关闭也会响铃ClockActivity 管理配置；可选 ClockService 处理事件；Host 持久调度闹钟并驱动时钟卡片Host 实时绘制时间、日期与下一闹钟
音乐离开页面仍播放，自动下一首MusicActivity 承载界面；PlaybackService 拥有队列与播放控制；共享 AppModel 保存账号曲目、艺术家、播放状态、进度与控制按钮

“同时在运行”指三个应用的功能同时有效，不要求三个界面持续绘制。PC 首版可以保留三个实例；天气和时钟无工作时进入 SUSPENDED，音乐继续 RUNNING。MCU 可在相同契约下回收闲置实例。

V1 不引入 Activity 栈、多窗口、多实例 App、Guest 线程、Binder、动态组件解析或可编程桌面布局。Home 直接调用 Host AppManager，普通 Guest 不开放任意跨 App 启动。

02参考 Android，但分清三个层次

Android 区分页面生命周期、应用进程存活和后台组件。MicroPixel 借鉴这种分工，裁剪为“一个 App 包＋一个可选 Activity＋一个可选 App Service；默认一个 Guest 承载”。下面的对应关系是本项目设计，不是 Android 状态机的复刻。

Android 概念保留的思想MicroPixel 简化
Activity 生命周期界面与后台业务分离，离开 / 返回有明确回调仅 NONE、CREATED、RESUMED、STOPPED；不设多 Activity 栈和部分可见状态。官方来源
Service 组件无界面，能独立于页面处理后台工作；默认不等于另一线程 / 进程显式 Start / Stop 与有界消息；默认同 Guest 串行分发，不实现 Binder 或绑定引用计数。官方来源
进程重要性系统按用户价值和资源压力管理存活实例分为前台、有效媒体、有限任务、闲置四种回收优先级。官方来源
Foreground service用户可感知的持续工作可以在页面不可见时继续PlaybackService 持有受 Host 核验的 media 租约；不额外创建 Guest。Home 展示当前播放工作。官方来源
App Widget桌面提供摘要与有限操作，点击可进入应用Host 模板＋状态快照＋操作事件；不嵌入另一个 Guest 的完整画面。官方来源
AlarmManager / 后台调度定时工作可独立于应用实例存活闹钟与周期任务分别由 Host 保存和触发，不依赖页面 Timer。官方来源
术语边界：Android 的 foreground service 不代表界面在前台；Android Activity 的 onStop 也不等于销毁进程。本文 STOPPED 专指“没有 Guest 实例”，不表示停用应用、删除数据或自动取消已经登记的闹钟。

保存配置应发生在业务修改提交时。不能把持久化依赖于最后一次退出回调；异常、强停和掉电路径不保证 Guest 有机会执行该回调。

03Android 差异与 RTOS / HMI 适用范围

适用结论：一个 App 一个 Guest、组件串行、Host 独占硬件的模型，能够承载天气刷新、闹钟和后台音乐共存。它提供的是精简应用框架；AppManager 的生命周期模型本身不提供内存保护。多实例准入、执行预算和故障边界必须同时成立。
维度AndroidMicroPixel / no-MMU 契约
内存与故障边界以 Linux 进程、UID 和内核沙箱隔离应用，原生代码也在进程边界内。官方来源独立线性内存＋Wasm 检查＋Host ABI 校验；RTOS 任务不是受保护进程。没有 MPU / PMP 等硬件保护时，Host 原生错误仍可能破坏整机。
组件与执行单元Activity / Service 是组件，Service 默认不另建线程，也可以配置独立进程。官方来源V1 一个 App 内组件共享 Guest 和串行事件循环；Activity Trap 会连带结束本 App 的 Service，其他 App 应继续。
UI 与后台调度完整窗口系统、页面栈、进程重要性和多种后台调度策略一个前台 Activity；后台 Service 只处理事件。Host 定时器、闹钟和音频设备独立运行；不追求所有应用持续占用 CPU。
通信Binder、系统服务和权限检查小消息复制、owner / epoch 校验、有界邮箱；不跨 Guest 共享指针、对象或任意可写内存。
绘制与桌面卡片应用窗口和 App Widget 由系统宿主展示Guest SDK 构建 Scene / Raster，Host 校验并呈现；Home 使用模板快照，不执行其他 Guest 的 UI 代码。
故障恢复可以结束独立应用进程，内核继续运行；也不保证内核或驱动缺陷无影响只对约定的 Guest 故障提供局部恢复；取消必须被运行代码观察到，不能把强删 RTOS 任务当作安全进程终止。

3.1 满足基本 HMI 的必要补充

现有 Guest UI 控件已有布局、文字、按钮、图像、列表行、滚动容器和 Slider，可覆盖简单天气页、闹钟配置页、音乐列表与播放页。组件框架需要统一页面创建 / 恢复 / 隐藏 / 销毁入口，不能由每个 App 自行管理显示租约。控件层与 AppManager 是两层契约。

  • 交互：唯一输入目标，页面切换取消按压与拖动；统一焦点、按键 / 编码器、文本输入和系统弹窗优先级。列表滚动触底与异步加载应由 SDK 统一表达。
  • 状态：加载、失败、空列表、重试与失效数据有明确显示；列表数据和播放队列归 AppModel，不能因页面销毁而丢失。长列表需窗口化或虚拟列表，避免为每首歌常驻创建全部节点。
  • 绘制预算：限制每 App 的节点、命令、纹理像素、解码尺寸、帧提交频率及处理时间；隐藏 Activity 不继续提交动画帧。Host 自己的 Home、系统弹窗和闹钟预留资源及调度时间。
  • 跨边界数据：Widget 文本 / 图片、绘图命令和资源包均作为不可信输入校验。图像解码器、字体解析器、网络协议栈属于 Host 可信计算基，不因输入来自 Wasm 就自动安全。
  • 无阻塞界面：HTTP、媒体解析和大资源读取走可取消的异步服务；LVGL 所在线程不运行 Guest 业务，不等待 Guest 回调，不持有跨 Guest 执行的全局锁。

3.2 MCU 资源与执行方式

RTOS 可为每个存活 Guest 配置一个受控执行任务，Guest 自身仍是单事件循环；Host UI、音频和管理任务独立调度。若要改为少量执行任务轮转多个 Guest，必须先把目前长驻 Guest main 改成有界 step / 可恢复执行模型，不能把可能永不返回的入口直接放进共享工作池。

MCU 的实例数、线性内存、任务栈、图形与媒体窗口按目标 profile 计费；PC 的四槽、每 Guest 16 MiB 和整曲解码缓存不能下放为 MCU 默认值。闹钟关键路径放在 Host 后，天气 / 时钟 Guest 可按需唤醒或回收，音乐只保留必要的 Service 与流式窗口。

04App、Activity、App Service 与 Guest 的关系

App / Bundle：安装、权限、配额、私有数据的边界
└── AppInstance：默认一个 Guest，一个串行事件循环
    ├── AppModel：共享的账号、设置与业务状态
    ├── Activity main（可选）：完整界面与用户输入
    └── Service main（可选）：后台事件与消息处理

Host：AppManager、MessageBroker、Scheduler、WidgetStore、
      AudioFocus、Time、Alarm，以及版本化能力接口

Activity-only、Service-only、两者同时具备都合法。普通 App 的 Activity / Service 不必分成两个 Wasm；一个 Bundle 中的静态组件注册表足够。V1 每 App 至多一个 Activity 和一个 App Service，后续扩展多个组件时再增加明确的容量。

App Service ≠ Host Service ABI。PlaybackService / WeatherService 是 Guest 内的业务组件；Network / Audio / Time Service 是 Host 提供的能力接口。前者调用后者。Service 也不等于一个操作系统线程，阻塞和解码工作仍交给 Host 异步能力。

  • OnCreate：本次组件对象的一次性初始化；随后 OnStart。Ready 后才交付首条业务消息。
  • OnMessage / OnScheduledWork / OnMediaEvent：按单一 Guest 事件循环串行处理；无事件时等待，回调不能自行阻塞网络或开线程。

可恢复的组件初始化失败只清理该组件：Service 启动失败不能销毁已在前台的 Activity；Activity 创建失败也不能停止正在播放的 Service。只有 Guest Trap、执行器故障或显式 StopApp 才走整个实例的停止路径。

4.4 AppManager 增加组件记录，而不是增加组件线程

AppManager 仍是唯一状态写入者；ActivityController 与 ServiceController 是它内部的逻辑控制块，共用同一个命令循环。前者处理界面对象与显示事务，后者处理 Start / Stop、组件 ready、工作计数与空闲策略。MessageBroker 管理有界投递；Scheduler 生成合法的唤醒票据。

同 App 已处于 STARTING 时，新的 Activity / Service 请求只合并为有界的组件启动意图，不再创建 Guest。实例 Ready 后分别推进组件；实例 Resume 只恢复执行，不自动对隐藏 Activity 调用 OnResume，消息唤醒也不创建界面。

同 App 组件共享内存与异常边界：Activity 的 Trap 可能终止同 Guest 的 Service。V1 以 App 为隔离单位；不能声称逻辑 Service 已实现进程级容错。将 Service 单独放到 Guest 是未来可选部署方式，需要显式预算和通信契约，不作为默认。

06实例身份与数据模型

AppId 是安装身份；InstanceKey = (boot_nonce, slot, epoch) 是一次运行的身份；request_id 标识操作；transition_seq 标识当前迁移。停止后重启同一 AppId，必须产生新 InstanceKey。

ComponentKey = (InstanceKey, kind, component_id, component_epoch) 标识 Activity 或 Service 的本次创建。销毁 Activity 再创建时，Guest 可完全不变，但 Activity epoch 必须变化，旧帧、输入与回复不能进入新界面。组件 token 用于路由与资源生命周期，不是同一 Guest 内的安全沙箱。

// Host 内部示意类型，不是 C ABI 的直接内存布局。
struct AppRecord {
    AppId app_id;
    PackageRevision package_revision;
    Lifecycle life;                 // 五种状态
    Optional<InstanceKey> instance;
    uint64_t transition_seq;
    Optional<PendingTransition> pending;
    ActivityRecord activity;        // NONE / CREATED / RESUMED / STOPPED
    ServiceRecord service;          // STOPPED / STARTING / RUNNING / STOPPING
    BackgroundLeases work;          // 固定容量，含原因、期限、所有者
    ResourceAccount resources;      // 内存、请求、流、句柄、包映射
    ExitReason last_exit;           // 失败是原因，不增设 CRASHED 状态
    bool user_stopped;              // 阻止非用户触发的自动重启
};

struct ManagerState {
    AppRecord catalog[64];
    InstanceSlot slots[4];          // STARTING / SUSPENDED / STOPPING 也占槽
    UiTarget ui;                   // Home 或有效 ComponentKey 指向的 Activity
    Optional<ForegroundRequest> pending_foreground;
};
身份 / 状态生命周期用途
AppId 与安装策略跨实例；可持久化私有 KV、任务配置、闹钟、Widget 声明、权限
InstanceKey本次运行服务句柄、HTTP、音频流、运行线程、回调所有者
ComponentKey本次组件对象Activity 显示 / 输入 / 图形子资源；Service 消息、媒体、网络与回复地址
transition_seq每次迁移递增丢弃迟到 READY / SUSPEND ACK / RESUME ACK
ForegroundRequest token每次用户切换递增加载 B 时又点击 C，B 完成后不得夺取 C 的前台
Widget revisionHost 对该 Widget 单调递增快照替换和过期操作识别；Guest 重启不会让旧卡片操作落到错误实例

Guest 调用身份由 GuestContext 注入，不能通过填写 AppId 冒充其他应用。持久配置按 AppId 保存，运行句柄按 InstanceKey 校验；两者不能混用。AppRecord 常驻不代表 Wasm 实例常驻。

ServiceRecord 至少保存 component_epoch、组件状态、空闲策略、未完成 work_id 与消息序列水位。有界消息存储只在存活实例槽内分配，不能为64个安装记录各预留一个完整邮箱。Activity 与 Service 可共享 AppModel，但不相互长期持有可销毁组件对象的裸地址。

Host 重启后所有实例状态从 STOPPED 开始，生成新的 boot_nonce；从策略库恢复 user_stopped、任务和闹钟登记，不恢复旧句柄或迁移请求。未被用户停止的天气可以按计划唤醒；闹钟由 Host 恢复；V1 默认不自动恢复音乐播放。

8.2 有界队列与关键通知

  • 普通命令队列有容量限制，满时返回 BUSY；不在实时路径扩容。
  • 停止意图与 RuntimeExited 使用每实例控制邮箱，不能被普通刷新命令挤掉。停止意图可合并，退出通知必须最终被消费。
  • 同一 App 的周期唤醒可合并为一次，记录 missed_count；不补跑几十次过期天气刷新。
  • 前台意图只保留最新一个 token；Widget 快照采用最后一份有效版本覆盖，业务操作事件不能用快照覆盖策略丢弃。
  • 同一 Guest 实例始终只有一个执行线程进入 Wasm。UI、网络线程与 AppManager 均通过事件通知，不重入 Guest。

09启动、切换、挂起与停止的时序

9.1 冷启动应用 B：先准备，再移交前台

  1. Home 或当前页面提交 Activate(B)。AppManager 生成前台 token，检查安装、策略、槽位与总预算。准入失败时保持原应用 A 和音乐不变。
  2. B 进入 STARTING，获得独立执行器、上下文和作用域服务。StartContext 携带启动原因、是否需要准备完整 UI、待处理操作；Host 可接受一个不可见 staging 帧。
  3. Guest 完成有界初始化，SDK 在进入事件循环时报告 RuntimeReady。后台启动可以没有画面；完整 UI 激活必须同时满足 RuntimeReady 和 FrameReady。等待时 Host 可显示 Loading 遮层，UiTarget 仍为 A，遮层暂时接管输入。
  4. 如果 token 仍是最新请求，Host 撤销 A 的输入、取消未结束手势、清除输入法待发送文本，撤销 A 的显示租约。
  5. 在一个显示提交中激活 B 的已准备画面并更新 UiTarget；输入仅在有效首帧就绪且无系统遮层后交给 B。向 A / B 投递有序的 VisibilityChanged。
  6. A 的媒体 / 任务资格继续有效；无工作时才进入空闲挂起流程。B 若在准备期间失败，A 不失去前台。
staging surface 是准备资源，不是屏幕拥有权。全局始终只有一个 DisplayLease。前台事务不等待 A 的业务回调返回才撤销其输入，但任何旧显示提交都必须经过租约校验。

前台启动窗口内若用户又点击 C 或返回 Home，更新 foreground token。B 的迟到完成只更新自身状态；若没有剩余合法工作，则取消或挂起 B，不提交其画面。

首帧超时与初始化失败都发生在移交前：撤销 B 的 staging 预算，清理 B，移除相应 Loading 遮层；最新意图未改变时恢复 A 的交互。不提供完整界面的应用不能成为 UiTarget，其显式操作作为后台工作执行。

9.3 挂起与恢复

  1. AppManager 确认应用隐藏、无有效后台租约、无业务操作待处理、不是最新前台准备目标，发送 PrepareSuspend(seq)，并阻止未经仲裁的新工作。
  2. Guest 在当前 handler 结束、进入 event_wait 安全点时配合；Host 完成作用域 I/O 处理与外借显示缓冲排空后报告 Quiesced。
  3. ACK 仍匹配目标时提交 SUSPENDED。业务时钟和普通 Timer 按现有冻结语义处理；Host 时间、闹钟与任务调度不冻结。
  4. 新的用户操作或任务到期触发恢复。先打开控制门，确认 Resume，再投递业务事件；Stop 控制始终可以唤醒挂起中的执行器。

挂起确认前出现新的工作时，取消该次挂起并提升序列。即使执行器刚好已停车，也必须解除停车；丢弃旧 ACK 本身不足以完成恢复。

10.1 三个应用如何协同

天气：Host 保存周期任务，合并到期唤醒；Guest 发布成功快照后结束 JOB。网络失败保留上次成功数据和时间，显示过期标记。周期刷新不能抢占前台。

时钟闹钟：Host 保存时区配置与闹钟；Guest 完成配置后可以挂起或被回收。时钟 Widget 仍持续更新。PC 首版允许实例驻留，以验证多实例隔离，不要求它不断执行。

音乐：后台继续处理网络和曲终事件，自动解析下一首；不进行进度条动画或完整 Scene 绘制。暂停时短暂保留执行资格，随后可挂起，但保留内存中的账号和队列；恢复不重新登录。实例被真正回收后只恢复明确保存的状态，不能承诺保留未选择持久化的凭证。

10.2 内存压力与优先级

先回收未使用的呈现缓存和解码缓存，再选择隐藏、无媒体与无有效任务的 SUSPENDED 实例；之后才考虑中止可重试的有限 JOB。前台与正在播放的媒体默认受保护。若仍不能准入新应用，返回 NO_CAPACITY，保持音乐继续，不通过静默杀音乐来假装启动成功。

LRU 只在同一保护等级内使用；不能让“天气最近刷新过”比“正在播放的音乐”更重要。真实 Host OOM 或设备关机属于异常边界，不提供绝对保活保证。

11.3 启动、消息和完成是三件事

  • StartService(service_id, optional_initial_message) 保证实例和组件初始化，在 ServiceReady 后交付首条消息。重复 Start 不重复创建对象。
  • SendMessage(endpoint, ...) 不默认创建另一个 Guest；目标挂起时按授权恢复。STARTING 可有限排队，STOPPING 返回 BUSY。
  • CompleteWork(work_id) 结束这一项工作；StopSelf(component_epoch) 另行核验消息 / 在途工作是否为空。不能把 Finish 某条消息等同于停止整个 App。

Accepted 仅表示已入队；业务完成另有 Reply / Result。队列满或 deadline 已到时明确拒绝。处理过程中取消属于尽力而为，不能承诺回滚已经发生的业务副作用。

载荷保存在 Host 有界邮箱，MessageArrived 事件只携带消息句柄等短描述，Guest 通过 Message Service 的 Read / Ack 复制并释放载荷；不把1 KiB载荷塞进现有固定事件结构。读取 ACK 与业务 CompleteWork 分离。等待消息最多8条，分发后的未完成工作受每 App 的工作配额约束；队列非空是有期限的唤醒意图，不能绕过 deadline 永久阻止挂起。

11.4 导出权限与可靠性

App Service 默认 exported=false，自身组件与可信 Home 可按声明调用。跨 App 消息必须显式声明 endpoint、允许发送者和消息类型；Host 限制载荷、频率、执行预算与唤醒来源。V1 不引入 Binder、通用广播、绑定引用计数或任意组件发现。

wake_on_message 默认关闭。接收服务显式开启且允许发送者 / 消息类型匹配时，Host 才能为跨 App 消息签发短期工作票据、冷启动目标 Service；仍受预算和 user_stopped 限制，不能借消息清除用户停止标记，也不能启动 Activity。实例端点的迟到回复永远不使用这条冷启动路径。

普通消息默认不持久化，崩溃后不自动重放。活动实例内按发送序列水位去重并缓存有限结果；缓存外的旧序列拒绝，不重新执行“下一首”等操作。跨实例恢复依靠幂等命令和状态查询，不承诺恰好一次。持久任务计划与闹钟登记走专用 Host 服务，不用普通消息模拟可靠调度。

Activity 销毁后，发给旧 Activity 的回复丢弃；已经交给 PlaybackService 的有效播放工作继续。Home 卡片可读取服务发布的新状态；重建的 Activity 通过查询或 AppModel 获取当前快照，不接收旧对象的迟到回复。

后台响应消息不等于抢占前台。除非有新的用户激活请求，Service 的定时工作、媒体结束或跨 App 消息都不能自行切换 UiTarget。允许导出字段也不等于自动脱敏，应用不得在公开回复或 Widget 中发布凭证。

13App 故障不扩散：故障模型与容器契约

这里的“WAMR 容器”指 Host 管理的模块实例、执行环境、线性内存和服务资源域，不是 Linux 容器或受硬件保护的进程。App 的 Activity 与 Service 默认共享一个故障边界。

可承诺的范围：在可信 WAMR、可信编译器和正确 Host 服务的前提下，Guest 的 Wasm Trap、资源超额和受预算约束的死循环只结束所属 App，不重启 Host，也不停止其他 App。无 MMU 且无额外硬件隔离时，不能承诺 WAMR / Host / 驱动的任意原生缺陷或任意恶意 AOT 机器码仍然可局部恢复。

执行预算分为独立三项：持续运行而未让出的上限、某次工作累计的计算额度、包含异步等待的总 deadline。ABI 调用不能无限刷新累计额度；合法 event_wait 可以暂停计算计费，但不能暂停工作 deadline。RTOS 时间片只保证任务有机会调度，不保证错误 App 已停止或资源已回收。

13.3 局部故障处理顺序

  1. SessionRunner 生成带 InstanceKey 的 Trap / Quota / Timeout 原因，AppManager 只修改所属 AppRecord。
  2. 撤销该 Activity 的输入和新帧提交；若它是前台则显示 Host Home / 错误状态。后台 App 故障不抢走当前前台。
  3. 禁止新服务调用，取消本 owner 的 I/O / 媒体与工作资格；受控运行代码观察取消标记并返回 Host。
  4. 确认执行任务退出，排空回调、借用缓冲和 DMA 后，才释放模块、资源与槽位。Guest OnDestroy 仅尽力执行，不在正确清理的关键路径。
  5. 保留 Widget 最后成功快照并标记离线；按 AppId 记录有界崩溃计数、退避及自动拉起熔断。Host 已登记闹钟继续有效。

原生 import 也必须有界：网络与解码等长操作交给可取消执行器，不能在 Guest 调用栈持有全局锁无限等待。若执行任务仍未退出，保持 STOPPING 和资源预留；禁止以强删任务、longjmp 跨原生资源栈或提前 free 伪装为安全回收。

若产品要求覆盖可信计算基的任意错误，需要额外设计硬件与权限边界：例如目标确实具备并启用 MPU / PMP、受保护任务 / 用户态、受限外设与 DMA 访问；或者采用有 MMU 的进程系统。这是另一个隔离 profile，不是 AppManager 状态机或切换解释器就能补齐的能力。

14AOT 可继续使用，但需可信构建与可中断执行

AOT 不等于取消沙箱。可信编译器可以把 Wasm 内存、间接调用和栈检查编译进原生代码；no-MMU 使用软件检查即可，不依赖 Linux 的 mmap / 信号页保护。风险来自关闭检查、原生产物来源不可信、无法限时退出或 Host 可信计算基缺陷。

  • Trap 已能返回 App 级失败：AppSession::Run读取 WAMR 异常并返回 GuestTrap / WatchdogTimeout。但这不捕获任意 Host 原生崩溃，也不证明其他 App 的资源不会被旧全局析构清理。
  • 终止请求不等于有界退出：watchdog超时调用 wasm_runtime_terminate()，固定版 实现主要设置异常标志。AOT 检查点生成受 thread manager 条件控制，且 check_suspend_flags()对非共享内存直接返回。当前 SDK 单线程 Guest 因而不能据此宣称纯死循环可在 watchdog 时限内退出。
  • 现有 watchdog 不是累计额度：ABI checkpoint 会重新延长 deadline；频繁调用 ABI 的忙循环不能仅靠这个计时器限制总计算消耗。需要独立预算，且不要为获取取消检查点而给 Guest 开启线程 / 共享内存。
  • AOT validator 不是机器码安全验证器：该固定版本 aot_validator.c只增加内存声明数量 / 导入限制检查；打开此选项不能证明原生指令保留了边界检查或未被篡改。
不要误用 instruction metering：上游 WAMR 构建文档明确限制该能力只支持 classic / fast interpreter，不适用于 AOT / JIT。AOT 的逐实例预算 / 取消需要另行确认并补足代码生成支持，不能只打开同名构建开关。

14.3 推荐执行策略

MCU 保留受控 AOT 作为性能路径，先补齐可信构建、软件检查、可中断执行和 owner 清理契约；解释器可作为开发和未知 Wasm 输入的受限执行路径，仍受 Host 可信计算基约束。PC RV32 的独立 QEMU 子进程可以被 Linux 终止，但该硬件 / 操作系统边界不等于 MCU 上已经具备同样的恢复能力。

对天气、音乐等普通业务，基本目标是“Guest 故障只结束本 App，Home / 其他 App / Host 闹钟继续”。对必须在本 App Activity 故障后仍连续运行的功能，应拆成 Host 受控服务或另一个 Guest 故障域，并为额外实例明确计费；仅增加一个 Service 类无法获得这种隔离。

15.2 更新、停止与恢复

  • 发布是有界复制，双缓冲或短锁交换后由 Home 读取；绘制过程中不执行 Guest，也不等待网络。
  • Host 对每张卡片维护单调 revision；拒绝同实例的倒序 provider_sequence，以及已关闭实例的更新。
  • 天气成功快照可缓存，音乐私有信息默认只在本次会话有效；注销时主动清除个人卡片，禁止快照携带凭证。
  • 应用停止不统一删除所有卡片。天气显示最后数据与新鲜度；时钟继续由 Host 驱动；音乐标记停止并禁用失效的播放状态。
  • 发布频率有配额。音乐在曲目 / 状态变化时发布，正常进度由 Host 推算；时钟不每秒发布。

15.3 点击卡片与按钮

点击卡片主体调用 Activate(ownerAppId)。点击按钮先验证当前卡片、操作声明与用户来源，再通过 AppManager 投递给所属 Guest：RUNNING 直接排队，SUSPENDED 先唤醒，STOPPED 按策略冷启动。UI 不直接调用 Guest 函数。

播放控制采用 SetPlaying(true/false) 等明确目标，避免重复 Toggle 翻转两次。“下一首”等非幂等动作按 requestId 去重，失败或崩溃后不自动重放；需要用户重新操作。结果通过新快照或操作完成事件确认，等待期间相应按钮暂时禁用。

旧 revision 的操作若会产生相反含义则拒绝，并要求 Home 刷新；通用“打开应用”可按当前登记重新解析。Widget 操作不能授权任意跨 App 控制，也不能在没有用户操作时偷偷切换前台。

16时间、闹钟与音频优先级

16.1 两类时间不能混用

时间用途规则
单调时钟启动 / 停止 deadline、工作租约、执行预算、退避不受用户改时间或网络校时影响；跨重启不能直接复用旧单调时间值
Host UTC ＋时区日期、每日闹钟、持久任务计划、Widget 更新时间校时 / 时区改变时重新计算下一触发点；对同一闹钟发生记录去重
现有 Guest 业务时钟动画、游戏逻辑、应用内部相对 TimerSUSPENDED 时可按旧契约冻结，不作为墙上时间或跨实例闹钟

原型使用 Host 统一配置的时区，默认 Asia/Shanghai（UTC+08:00）。V1 不开放尚未实现转换规则的夏令时地区配置；如扩展时区库，必须同时定义不存在时间与重复时间的触发策略。

16.2 闹钟属于 Host 的持久登记

登记至少包含 (AppId, alarm_id, rule_revision, enabled, local_time / UTC, repeat_rule, timezone, ring_profile)。写入成功才返回已保存；失败保留旧规则。Guest 不存在、被用户停止或发生异常时，已登记闹钟仍可由 Host 响铃；Host 是否重新唤醒 Guest 另受 user_stopped 约束。

每次触发生成稳定的 occurrence_id，例如“应用＋闹钟＋规则版本＋本地发生日期”。先记录待响意图，再请求 Host 铃声。用户关闭或稍后提醒后提交对应状态；重启恢复未确认提醒时，只维护一个活动响铃实例。

不宣称跨掉电的外部声音动作可以绝对“恰好一次”。使用持久发生标识与确认状态恢复，允许同一未确认提醒恢复响铃，但不产生并行重复响铃。时间回拨不重复启动已处理的同一发生记录；大幅向前校时按可配置的迟到窗口处理。

默认建议：短时间错过的提醒可以补响一次；超出迟到窗口只记录错过并安排下一次。设备休眠唤醒取决于平台能力；完全断电时的软件定时器不能保证响铃，Time / Alarm 服务应报告对应能力。

16.3 音频重要性不等于界面前后台

普通天气页面进入前台不应自动暂停音乐。V1 同时允许一个媒体拥有者与一个 Host 闹钟输出；多个普通媒体流的替换 / 拒绝由 Host 明确仲裁。系统主音量始终独立于 App 音量与 focus 增益。

  1. AlarmScheduler 触发后，AudioFocus 为 Host 闹钟获得临时优先级。
  2. 支持混音的平台降低音乐 focus 增益并播放铃声；不支持的平台暂停对应媒体流并标记原因是 focus interruption。
  3. 音乐仍保留原实例和媒体资格。因闹钟被暂停时，不触发普通的“长时间无进展 / 暂停宽限到期”回收逻辑。
  4. 结束时仅撤销该次 focus 影响。恢复前核对流身份与用户播放意图版本；如果用户期间暂停、换歌或停止应用，不能凭旧记录重新播放。

闹钟声源与停止 / 稍后提醒入口由 Host 管理。即使 Clock Guest 正在启动、卡死或已停止，Home 系统提醒仍能关闭当前铃声。停用或卸载所属应用时，必须先禁用相关发生记录并撤销响铃租约。

  • 当前音乐应用需要把界面与微信扫码视图放入 MusicActivity，把队列、播放、自动下一首和 Widget 发布放入 PlaybackService；共享账号归 AppModel，登录界面请求与播放请求使用不同组件归属。

19必须保持的不变量

  1. 唯一实例：任意 AppId 至多一个存活实例；正在清理的实例仍算存活。
  2. 唯一显示权：任意时刻最多一个 Guest DisplayLease。Home 与系统提醒由 Host 接管。
  3. 停止局部化：停止天气不能结束音乐流、取消音乐请求、清除音乐场景或解绑其他实例输入。
  4. 组件独立：停止 / 销毁 MusicActivity 不停止 PlaybackService；停止 Service 也不自动销毁仍在前台的 Activity。
  5. 组件不等于实例：每个 App 默认一个 Guest；组件通过同一事件循环执行，共享 App 级异常边界。
  6. 前台与音频独立：天气进入前台后，音乐继续播放并处理下一首。
  7. 安全回收：RUNNING 不直接释放；SUSPENDED 回收也必须经过 STOPPING 与清理确认。
  8. 时间独立：实例挂起或退出不冻结 Host 时间，不取消已经确认且未禁用的闹钟。
  9. 回调不可串代：旧实例的 HTTP、音频、图像与迁移回调不能改变新实例。
  10. 用户意图最新优先：连续激活 A、B、C 后，迟到完成不能使前台从 C 跳回 A / B。
  11. Home 绘制独立：Guest 阻塞、异常或不在线时，Home 可以继续显示可用缓存及 Host 时钟。
  12. 有界资源：命令、队列、租约、快照、请求、图形和重启都有明确上限；超限不靠隐式增长掩盖。
  13. 故障边界明确：Guest Trap 与可中断的预算耗尽只终止所属 App；Host 原生错误和未知来源 AOT 不伪装成可局部恢复的普通 App 故障。
  14. 可停止先于准入：执行后端必须满足逐实例取消和有界返回契约；watchdog 发出终止请求本身不是退出证明。
  15. 凭证归属：音乐 Cookie 与队列业务留在音乐 Guest；Home 只接收允许展示的摘要。
  16. 恢复正确：闹钟结束只能恢复仍有效的音乐意图，不能重新播放用户已暂停或停止的内容。

词本文含义

    
App安装与权限边界，包含可选 Activity 和 App Service；不等于一个永远存在的进程

    
ActivityGuest 内的完整界面组件；STOPPED 只是隐藏，不表示 Guest 停止

    
App ServiceGuest 内按事件执行的后台业务组件；默认与 Activity 共用实例和线程

    
Host Service ABINetwork / Audio 等跨边界能力接口，不是 App 业务 Service 对象

    
实例 / Session一次独立 Guest 执行及其资源归属

    
RUNNING可以处理事件，不代表持续占用 CPU，也不代表可见

    
后台没有前台 UI；可 RUNNING，也可 SUSPENDED / STOPPED

    
租约Host 授予的有限资源 / 执行资格，不是 Guest 自报的永久权限

    
WidgetHome 渲染的跨应用卡片协议，不是 Guest 内部 UI 控件实例
